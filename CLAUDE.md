# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

ts-sql-query is a type-safe SQL query builder (not an ORM) for TypeScript that supports MariaDB, MySQL, Oracle, PostgreSQL, SQLite, and SQL Server, running on Node.js (>=22) and Bun. Published documentation lives at https://ts-sql-query.readthedocs.io/ and is built from [docs/](docs/) with `mkdocs`.

## Commands

The project supports both Node and Bun. **For the `test/` matrix, prefer bun** (`bun run tests …`): since Bun 1.4, `bun test --parallel --no-isolate` (passed by default by [`scripts/_test-common.sh`](scripts/_test-common.sh)) keeps one global + module registry per worker — the same model as vitest's `isolate: false` in [`vitest.config.ts`](vitest.config.ts) — so the DB pool + schema bootstrap is built once per worker, not per file. With it bun is faster on every loop and uses far less memory, and it is the only runtime that runs the Bun SQL cells (`bun_sql_*`, `bun_sqlite`) against their engines. The `node_sqlite` cells (+ their `-sync` twin) run under Bun against Bun's own `node:sqlite` implementation, so a full real validation adds `npm run tests -- --run-connectors native` to validate Node's. `--isolate` on the tests CLI restores per-file isolation to debug a cross-file leak. The figures are in [`test/BENCHMARKS.md`](test/BENCHMARKS.md), the only place that keeps exact counts and timings. **The other dev scripts are runtime-agnostic** — `validate*` / `build` invoke a compiler (TypeScript 7's `tsc`, a native binary), so the launcher is irrelevant, and `tests:where-is` runs within noise either way (searcher startup 0.02 s bun vs 0.28 s tsx). **One script is not runtime-agnostic: `tests:index`** — prefer `npm run` (node, faster with the same peak; `bun run` runs it on bun) and the script tunes the runtime itself; if a build ever fails, `scripts/tests-index.sh --help` has the escape hatches. (Note: node can't run these `.ts` tools *natively* without a loader — this repo's mandatory `.js`-extension imports point at `.ts` files, which node's built-in type-stripping doesn't remap; tsx/bun do. A node-native path needs a tiny resolve-hook and buys nothing over tsx, which is a required dep anyway.) The **publish pipeline and CI stay on npm/Node** — keep both paths working. Each script in `package.json` has a **single name** (no `bun:`-prefixed twin): the underlying shell script detects whether `bun run` or `npm run` invoked it (via `npm_config_user_agent`) and dispatches to `bun test`/`bun run` or `vitest`/`tsx` accordingly. (Command examples below are spelled `npm run tests -- …` — mind the `--` separator, see the npm gotcha below; the bun spelling is `bun run tests …`, no separator.)

It measures the library without its query runners; the runners have their own report, `bun run coverage:runners` (`--coverage-scope runners` over the `test/runners/` tests, every runner against its engine — see [`test/CLI.md` § Coverage of the query runners](test/CLI.md#coverage-of-the-query-runners)), and so do the error mappers, `bun run coverage:mappers` (`--coverage-scope mappers`, the same tests' real-error scenarios). Full guide split per topic — see [`test/README.md`](test/README.md) for the navigation map; rules live in [`test/DESIGN.md`](test/DESIGN.md), commands and flags in [`test/CLI.md`](test/CLI.md), wall-time numbers in [`test/BENCHMARKS.md`](test/BENCHMARKS.md).

    - `bun run tests --docker` — same matrix, docker-backed connectors hit their real DB (container reuse on by default). **Over 10 minutes with warm containers**, under bun or vitest; vitest mocks the Bun SQL cells ([`test/BENCHMARKS.md` § Cross-runtime timings](test/BENCHMARKS.md#cross-runtime-timings)).
    - `bun run tests --docker newest` — smoke against real DBs but only on `<db>/newest/*` cells; older docker cells still RUN but mock (`newest` is a value of `--docker`).
    - `bun run tests --run-versions newest` — skip older-version cells entirely (participation: paths). The runner is invoked on `<db>/newest/*` + `<db>/types.negative/*` only — different from `--docker newest`, which keeps the older-version tests running through the mock. Main use: shorter coverage runs when older-version coverage is redundant with the matching newest cell.
    - `bun run tests --run-connectors <all|docker|wasm|native>` — **participation** filter by connector kind (which cells RUN). `wasm` = pglite + sqlite-wasm-OO1(+sync); `native` = embedded SQLite drivers (better-sqlite3(+sync), bun_sqlite(+sync), bun_sql_sqlite, node_sqlite(+sync)) that need no extra infra; `docker` = everything else (containerised engines). It EXCLUDES the other kinds from the run (does not mock them). The canonical "real WASM only" run is `bun run tests --run-connectors wasm --wasm`. Vocabulary mirrors `RealDbBackend` in [test/lib/backends.ts](test/lib/backends.ts); the folder-name lists live in `WASM_CONNECTOR_NAMES` / `NATIVE_CONNECTOR_NAMES` in [`scripts/_test-common.sh`](scripts/_test-common.sh) (KEEP IN SYNC — the `-sync` twins belong to the same kind as their async cell).
    - `bun run tests --docker --wasm` — full real coverage (sequential real-WASM pass first, then the parallel main pass). The WASM phase runs **every** wasm cell real — pglite + sqlite-wasm-OO1(+sync) across **all** version tiers — plus the query-runner tests of those engines.
    - `bun run tests --shard [<n>]` — **no-docker CI split.** The full mocked matrix + real WASM (what `test:no-docker` covers) run as one process peaks ~15.9 GB and **OOMs the 16 GB CI runner on Node 26** at the final aggregation. `--shard` partitions it into **4 memory-bounded groups** (~8 GB peak each), each a separate runner invocation so memory frees between them. Bare `--shard` runs all four in sequence; `--shard <n>` (1..4) runs just one (CI uses one step per shard — see [.github/workflows/ci.yml](.github/workflows/ci.yml)). Shard 1 = all wasm cells + the query-runner tests of those engines, real+sequential; 2/3 = sqlite native groups; 4 = the rest (docker mocked + docs + types.negative + query-runner tests). No test runs twice. Full-matrix / no-docker only — rejects coords, `--coverage`, `--docker`, `--run-connectors`, `--run-versions`. Partition + shard membership live in `shard_paths` in [`scripts/_test-common.sh`](scripts/_test-common.sh); full detail in [`test/CLI.md` § Sharding](test/CLI.md#sharding).
    - `bun run tests <coord>…` — focused run on one or more positional coords (same script, same flags as the full-matrix invocation, just a narrower path set). Supports glob (`*`) and brace (`{a,b}`) expansion, quoted or not: `bun run tests 'postgres/*/pg'`, `bun run tests 'postgres/*/{pg,postgres}' --run-versions newest`, `bun run tests postgres/newest/pg sqlite/newest`. `--wasm` becomes a single-pass override in focused mode (the two-phase split fires only on the full matrix).
    - `bun run tests:runners` — the query-runner tests in [`test/runners/`](test/runners/) (outside the cell matrix: each exported runner called directly with hand-written SQL; `--docker --wasm` to run every runner against its engine; coord root `runners`, e.g. `bun run tests runners/postgres --docker`). See [`test/RUNNER_TESTS.md`](test/RUNNER_TESTS.md).
    - `bun run tests:audit` — symmetry audit across every `(db × version × connector)` cell. Pre-merge check.
    - `bun run tests:stop-containers` — stop the warm docker containers `--docker --docker-mode reuse` left running.
    - `bun run tests:reopen` — re-open the previously generated `--report` / `--coverage` HTML without re-running tests.

**ONE HEAVY JOB AT A TIME — NON-NEGOTIABLE.** Never have two heavy jobs in flight at once. The heavy set is: `bun run tests` (whole matrix, with or without `--docker` / `--wasm`), any `tsc` invocation (`validate`, `validate:tests`, `validate:tests:newest`, `build`), `bun run tests:audit`, `npm run tests:index*`, and `bun run all-examples` / `no-docker-examples`. This project is large enough that any two of them together exceed RAM: the whole-matrix vitest run peaks ~15.9 GB on its own and the per-connector tsc split peaks ~8 GB, so a second job means the OS OOM-killer takes one of them out.

Start one, **wait for it to finish, then start the next**. Backgrounding one and launching another "while it runs" is the same violation — it is precisely how the OOM happens. Filling the wait with cheap work (reading files, small greps, editing docs/tests) is fine; anything that competes for RAM or CPU is not. To watch a long run's log, use a blocking waiter (`until grep -q … ; do sleep 15; done`), never a second workload.

**The database engines are a second consumer of the same budget — count them.** When `--docker` is in play the containers are not free bystanders: measured at REST right after a full matrix run, SQL Server holds ~3.1 GB, Oracle ~2.6 GB, MySQL ~0.8 GB, MariaDB ~0.36 GB and PostgreSQL ~0.32 GB — **~7.2 GB of engines**, inside a Docker VM provisioned ~11.7 GB of host RAM whether or not the engines are busy. So a `--docker` run has already committed most of the machine before the first test executes, which is why there is no headroom left for anything else. Under load it is higher than the at-rest figures above.

Worse, **container reuse holds that memory between runs.** `--docker-mode reuse` is the default, so the engines stay up after the run finishes — a `tsc` started "now that no tests are running" still competes with ~7 GB of idle containers. Run **`bun run tests:stop-containers`** before a heavy non-docker job (or when handing the machine back), and remember the first `--docker` run after that pays the cold-start cost again.

Two failure modes make this expensive to diagnose, which is why it is a hard rule and not a preference:

- The victim dies with **`EXIT=137`** (SIGKILL) — often *after* many minutes of wall-time, and with no test summary printed, so the log looks truncated rather than killed.
- The survivor emits **bogus failures**: CPU starvation pushes tests past the 60 s per-test timeout, and a contention timeout is indistinguishable from a real regression in the output. Any failure from a run that overlapped another heavy job must be **discarded and re-run alone**, never interpreted.

This applies to the agent itself, not just to delegated subagents — see also [`test/BENCHMARKS.md`](test/BENCHMARKS.md) and [`test/CLI.md` § One heavy job at a time](test/CLI.md#one-heavy-job-at-a-time).

**Test-loop discipline — start narrow, widen only when needed.** The full `test/` matrix holds hundreds of thousands of tests across over 20k files. Running it on every inner iteration adds up fast. The cells are heavily symmetric — for most changes the older-version cells emit the **same** snapshots as the matching newest cell (same SqlBuilder, same expressions), so re-running them is wasted feedback. Default order of preference (commands via `bun run tests …`):
1. **`tests <coord>`** — when iterating on a single cell or file (the typical case while editing). Tightest loop.
2. **`tests --run-versions newest`** — when a change spans multiple databases. Skips the older version tiers entirely, and with them most of the redundant assertions.
3. **`tests`** — full matrix, mocked. Use as the **pre-push** sanity sweep, not during iteration.
4. **`tests --docker` / `--wasm`** — only when the change touches a docker-backed connector or the WASM path, or as the final confidence check before pushing. Run them under bun (`bun run tests --docker`) — it also validates the Bun SQL cells — and add `npm run tests -- --run-connectors native` to run the `node_sqlite` cells against Node's `node:sqlite`. Real-DB cells are the slow lane regardless.

Widen the scope explicitly when you have a specific reason: touching a compatibility-version branch in a `SqlBuilder`, investigating a regression that might be version-specific, or pushing a release-blocking change. Otherwise, narrow stays the default.

**Narrowing a run — first-class flags** — to filter by test name or refresh snapshots, use the script's own `--test-name-pattern <regex>` and `--update-snapshots` flags rather than forwarding the runner's flags after `--`. The script translates them to the active runner's spelling (bun's `--test-name-pattern`/`--update-snapshots` vs vitest's `--testNamePattern`/`--update`), so the same invocation works under `bun run` and `npm run`. The canonical "fix one test's snapshot" recipe is `bun run tests <coord> --test-name-pattern inner-join --update-snapshots` (combine with a coord or a pattern — `--update-snapshots` over the full matrix rewrites every snapshot and the script warns). `--bail [<N>]` (stop after N failures, default 1) cuts wall-time in the iterate-on-one-cell loop, `--timeout <ms>` overrides the per-test timeout (default 60000; raise it to debug a slow docker cell, lower it to fail-fast on a hang), and `--no-color` (sets `NO_COLOR=1`) keeps output clean for `grep`/`tail`. Reserve pass-through after `--` for runner-specific flags the script doesn't wrap. See [`test/CLI.md` § Narrowing inside a coordinate](test/CLI.md#narrowing-inside-a-coordinate).

**Inventory before propagating — `--list-cells` / `--list-cells-with-mode` / `--list-files` / `--list-tests`** — four mutually-exclusive terminal listing flags, at increasing granularity. `--list-cells` enumerates the active cells (`test/db/<db>/<version>/<connector>`); `--list-files` enumerates the `*.test.ts` files (the level you copy-bake during propagation). Both are runner-free filesystem walks: deterministic, runtime-agnostic, honour all the path filters, and replace hand-rolled `for db in test/db/*/…` loops (e.g. the propagation step in [`test/COVERAGE_RUNBOOK.md`](test/COVERAGE_RUNBOOK.md)). Their per-database/​per-cell counts match `bun run tests:audit`. `--list-cells-with-mode [running|all|real|mock|skipped]` considers the **whole matrix** and annotates each cell with a verdict + reason: `real (docker|wasm|native)`, `mock` (its kind's `--docker`/`--wasm`/`--native` selection didn't include it — the test still runs against the mock), or `skipped` (EXCLUDED from the run — `outside coords`, `excluded by --run-connectors`, or `excluded by --run-versions newest`). The optional filter defaults to `running` (cells that will run: real+mock), with `all` (whole matrix incl. skipped), `real`, `mock`, `skipped` to narrow; a footer tallies running cells and other-cells-skipped separately. The real/mock projection mirrors `isRealDbEnabled()` in [`test/lib/backends.ts`](test/lib/backends.ts) via the `cell_mode` helper in [`scripts/_test-common.sh`](scripts/_test-common.sh) (marked `KEEP IN SYNC` — update both if the gate logic changes). `--list-tests` enumerates the test *names* a selection would run (to review what already exists before deciding where to add coverage, or to preview a `--test-name-pattern`) — it's the one **vitest-backed** flag (bun has no collect-only mode, so it always shells out to `vitest list`; not runtime-agnostic). For the same real/mock breakdown *after* a normal run (the "mock-validated vs real-validated" round-closing report), pass `--validation-summary [running|all|real|mock|skipped]`. Usage: `bun run tests [<coords>] [--run-versions newest] [--run-connectors …] --list-{cells,files,tests}` / `--list-cells-with-mode` / `--validation-summary`.

**npm flag-forwarding gotcha** (only when you deliberately run under npm — e.g. the node `--run-connectors native` pass) — under `npm run`, bare `--flag` tokens are consumed by npm itself as config (you'll see `npm warn Unknown cli config "--flag". This will stop working …`) and never reach the script. Use the `--` separator: `npm run tests -- --docker --run-versions newest`, not `npm run tests --docker --run-versions newest`. Bun does not have this problem — `bun run tests --docker` works as expected. This applies to the first-class flags above too — under npm they still ride behind the single `--` (`npm run tests -- <coord> --test-name-pattern inner-join --update-snapshots`), they just no longer need a *second* `--` or runtime-specific spelling. When mixing script flags with genuine runner pass-through under npm, the pattern is `npm run tests -- <script-flags> -- <runner-args>` (e.g. `npm run tests -- --docker -- --rerun-each 3`).

**Reserved names** — `test` and any `test:*` in `package.json` are **user-only aliases**. The agent must use the canonical `tests` / `tests:audit` / `tests:stop-containers` / `tests:reopen` instead. If you see `test` / `test:foo` in `package.json`, assume the user added it as a personal shortcut and **do not run it** unless explicitly instructed; treat it as opaque.

## Testing strategy

Two suites coexist. The new one is gradually replacing the legacy one — both have to stay green until parity is reached.

**Legacy: [`src/examples/`](src/examples/)** — runnable example scripts, NOT unit tests. The rationale that drove this layout:

- Each example exercises the **public API only**, so it doubles as user-facing reference code.
- The same scenario is implemented per database (`PgExample.ts`, `MySql2Example.ts`, `MariaDBExample.ts`, `OracleDBExample.ts`, `MssqlTediousExample.ts`, multiple SQLite variants) and per query runner / driver combination (better-sqlite3, mariadb, mssql, mysql2, oracledb, pg, postgres, Bun's built-ins, etc.).
- [src/examples/documentation/](src/examples/documentation/) holds per-database scripts that run the documented scenarios. The docs don't render their output: the code blocks of the docs are compiled and their SQL asserted by `bun run codegen:doc-code` (see [`test/DOC_CODE_EXTRACTOR.md`](test/DOC_CODE_EXTRACTOR.md)).
- The docker-backed examples run against real database servers; mocks are avoided.
- **Only minimal changes here**: remove a workaround, or restore parity with the sibling example of another database. New coverage goes to `test/`.
- Some examples are guarded by Node-version checks inside [scripts/no-docker-examples.sh](scripts/no-docker-examples.sh) and [scripts/all-examples.sh](scripts/all-examples.sh) (inside the `else` branch — `$runtime = "bun"` skips them). Today `NodeSqliteExample.ts` and `NodeSqliteSynchronousExample.ts` are skipped on Node 22 (they use `DatabaseSync.function()`, which is only available from Node 24) and run with `NODE_OPTIONS='--experimental-sqlite'` on Node 24+ (no longer needed since Node 22.13, and harmless). When adding an example that depends on a Node feature introduced in a specific version, follow the same `if [ "$NODE_MAJOR" -ge N ]; then … else echo "Skipping …"; fi` pattern instead of failing the whole script.

**New: [`test/`](test/) matrix** — the future. Per-cell `.test.ts` files asserting SQL + params + result type + value, running under either `bun:test` (default) or `vitest` (opt-in for the rich coverage / report stack). The same code path runs in both **mock** and **real-DB** modes — mocks aren't avoided here, they're the default fast loop and the docker-backed real DBs are an opt-in (`--docker`). For the design rationale see [`test/DESIGN.md`](test/DESIGN.md); [`test/README.md`](test/README.md) is the navigation map (which doc to read for which task).

**A bug found while testing or reviewing docs is fixed in `src/` directly**, with a test that fails before the fix and passes after on the engine where it happened, plus a changelog entry if the bug existed in a published version. Ask the maintainer first when the fix changes behaviour that a test fixes on purpose or that the docs promise. [`test/BUGS.md`](test/BUGS.md) (with a `// TODO[BUG]` next to the assertion) holds only what is found and left for later. Work the maintainer decided to do later is listed in [`test/DEFERRED.md`](test/DEFERRED.md).

**Working documents in `test/`** (campaign manuals, ledgers, audit reports) are throwaway: never link them from `test/README.md` or from a permanent doc.

## The library's golden rule — only the query you asked for

**The library sends to the database only the query the user asked for.** The exceptions are `executeSelectPage` (two queries: the rows and the count) and the statements of a transaction (begin, commit, rollback), which go their own way. **Never add a query of its own** — not a probe to read a state (`do 0`, a `begin` to see whether SQLite is in a transaction, `select @@in_transaction`, `select @@trancount`), not a `select changes()` after a statement, not even only after an error: the network round trip between the backend and the database is expensive, and it is a cost the user didn't ask for. Read what you need from what the driver already gives (the result, the error, a flag of the connection, a driver event); when the driver gives nothing, don't do it and document the gap ([`test/LIMITATIONS.md`](test/LIMITATIONS.md)).

Known exception, kept on purpose: `Sqlite3WasmOO1QueryRunner` reads the id of the inserted row with `select last_insert_rowid()` only for an insert without `returning` (the library builds one only for a `compatibilityVersion` below SQLite 3.35, older than any sqlite-wasm build): the OO1 `Database` gives no other way, and the engine runs in the same thread. Don't copy this pattern elsewhere.

## Other library rules

- **Never throw to pre-empt an error of the database.** A guard goes only where that very query would silently give a wrong result and no emission works. Otherwise change the SQL so the query works. Precedent: commit `745a0810` removed `HAVING_COLUMN_SHADOWED_BY_GROUP_BY_COLUMN` on MySQL/MariaDB and writes the column as its expression instead.
- **The code reads left to right, and the result is the same rows on every database.** `a.union(b).intersect(c)` is `(a union b) intersect c`, whatever precedence the engine gives the operators. Different rows per database is a bug.
- **The query runner and the connection.** The query runner owns how a parameter reaches the database: its placeholder, the cast in it or the type it's sent with (a cast, a type of the driver, an OID), and the checks of the value sent (a `customDecimal` too wide for the database), after the type adapter, so they cover every parameter, also one added to SQL the user writes. That holds even when the rule is the same for every driver of a database: it lives in one module per database (`src/utils/postgreSqlParamTypes.ts`, `mySqlParamTypes.ts`, `sqlServerParamTypes.ts`, `oracleParamTypes.ts`), and each runner's `addParam` is a binding in `src/utils/queryRunnerParams.ts`, the same one `MockQueryRunner` calls to imitate it. The query runner also owns which per-query options make the driver hand over a value without loss (text instead of a rounded number, a `BigInt` instead of a rounded integer) and the shape of what it returns. It decides with what the params carry: the type of each parameter (`getQueryParamType…`), whether it is the value of a column (`isQueryParamValueForColumn`), the expected type of each result column (`getQueryResultColumns`) and the connection's configuration (`getQueryConnectionConfiguration`). It never changes the meaning of a value. The connection and the SQL builder own the library's semantics: the SQL around the values and the SQL of the result columns (like the `convert` of a `customDecimal` on SQL Server), how a value of each type is converted (`transformValueToDB` / `transformValueFromDB`), and which value a type promises. A runner that can't do its part does nothing, and the library works as before.
- **No recursive types in the library.** Use numbered levels, as in [src/complexProjections/](src/complexProjections/); a depth counter counts as recursive. A TS2589 on an `Exact` assertion means too much branching: reduce it, never weaken the assertion.

## Architecture

The library is layered. Read top-down when tracing a query through the system:

1. **User-facing entry points** (`src/Connection.ts`, `src/Table.ts`, `src/View.ts`, `src/TypeAdapter.ts`, `src/Values.ts`, `src/TsSqlError.ts`, `src/dynamicCondition.ts`) plus the public sub-trees enumerated in [package.json](package.json)'s `exports` map (`src/connections/*`, `src/queryRunners/*`, `src/extras/{IDEncrypter,sync,types,utils}`) are the only stable public surface. Anything outside that list (notably `src/internal/`, `src/queryBuilders/`, `src/sqlBuilders/`, `src/complexProjections/`, `src/expressions/`, `src/utils/`) is implementation detail and may change — reachable only via the `__UNSUPPORTED__/*` escape hatch in `exports`.
2. **Per-database `Connection` subclass** in [src/connections/](src/connections/) (e.g. `PostgreSqlConnection`, `MySqlConnection`, `SqliteConnection`, `OracleConnection`, `SqlServerConnection`, `MariaDBConnection`). Users subclass one of these and define their tables/views/sequences/procedures on it. All share `AbstractConnection` / `AbstractAdvancedConnection`.
3. **`SqlBuilder` for that database** in [src/sqlBuilders/](src/sqlBuilders/) (one per backend, all inherit `AbstractSqlBuilder` — ~3k lines and the heart of dialect handling). The Connection wires itself to its SqlBuilder in its constructor.
4. **`QueryBuilder` family** in [src/queryBuilders/](src/queryBuilders/) (`SelectQueryBuilder`, `InsertQueryBuilder`, `UpdateQueryBuilder`, `DeleteQueryBuilder`, `FragmentQueryBuilder`, `DynamicConditionBuilder`, `SequenceQueryBuilder`) — fluent builders returned to the user; they accumulate state and hand it to the SqlBuilder when an `execute*` method is called.
5. **Value expressions** in [src/expressions/](src/expressions/) define the type-safe expression tree (`values.ts` is the master list of `*ValueSource` interfaces); [src/internal/ValueSourceImpl.ts](src/internal/ValueSourceImpl.ts) implements them.
6. **`QueryRunner`** in [src/queryRunners/](src/queryRunners/) abstracts the underlying driver — per-driver runners (`PgPoolQueryRunner`, `MySql2QueryRunner`, `BetterSqlite3QueryRunner`, …), Bun-native runners (`BunSqliteQueryRunner`, `BunSqlPostgresQueryRunner`, `BunSqlMySqlQueryRunner`, `BunSqlSqliteQueryRunner`), Node-native (`NodeSqliteQueryRunner`, 24+) and wrappers (`ConsoleLogQueryRunner`, `InterceptorQueryRunner`, `MockQueryRunner`). A Connection accepts any QueryRunner — this is the seam users override to log, mock, or chain behavior. The `test/lib/mockRunners/` folder contains connector-specialised `MockQueryRunner` subclasses for the runners whose `addParam` does observable transformations the generic mock doesn't replicate; see [test/lib/mockRunners/README.md](test/lib/mockRunners/README.md).
7. **Complex projections** in [src/complexProjections/](src/complexProjections/) implement nested object selection, optional-as-null vs optional-as-undefined, aggregated-array projection, left-join handling, picking, and compound queries. Two separate result-shape projectors exist (`resultWithOptionalsAsNull` vs `resultWithOptionalsAsUndefined`) — when adding result-shape logic, update both.

[src/examples/documentation/simplifiedQueryDefinition.ts](src/examples/documentation/simplifiedQueryDefinition.ts) is a hand-maintained simplified view of the public type surface — useful as a map when navigating the heavily generic real types.

## Code navigation — searcher before textual search on TypeScript

**Before any textual search over `src/` or `test/db/`** — by **any** means that matches characters rather than resolved symbols (the Grep tool, ripgrep, `find` over file contents, `awk`/`sed`, a Bash one-liner, a shell pipe, an MCP search, opening files by hand to scan them, anything else of that shape) — read [`test/CODE_SEARCH.md`](test/CODE_SEARCH.md) **in full once at session start**. Doors, sections, presets and reading conventions are all operational, not optional. Pay special attention to [§ "This tool vs. textual search"](test/CODE_SEARCH.md#this-tool-vs-textual-search): it is the gate that decides searcher vs textual search per question. Then reach for `tests:where-is` instead. The searcher runs against a resolved semantic index — the compiler's view of the code — and answers TypeScript-shaped questions textual search cannot model: declarations across all overloads, type-argument blast radius (where an alias is used as a type arg), call-chains, implementer classes, brand sites, public-surface vs internal classification, and the cross-world (`src/` + `test/` matrix + `docs/` + `src/examples/`) trail of a single symbol. Recent miss: a bug fix searched textually across the two files the BUGS.md entry named (`View.ts`, `Values.ts`) and left a third (`Table.ts`) regressed; `tests:where-is --search virtualColumnFromFragment --declared full` would have listed all three in one report.

```bash
npm run tests:index:newest     -- # refresh the index, NEWEST cells only — the low-RAM/faster session default
npm run tests:index            -- # refresh the FULL index (all version tiers + domain); heavier build
bun run tests:where-is --help  # doors / sections / presets
```

Index once per session and query it from then on: one indexed query beats several rounds of textual scanning and catches what they silently miss. **Prefer `tests:index:newest`** for the once-per-session build — it drops the older version tiers (`<db>/oldest/`, `<db>/8_000_000/`, …) and `<db>/domain/` cells, so it uses less RAM and builds faster while still indexing all of `src/`, docs, examples and the `newest` + `types.negative` cells the agent works with day-to-day (the index records `meta.scope` = `newest` vs `full`). Reach for the full `tests:index` only when a query must reach an older-tier or domain cell — e.g. investigating a version-specific regression. Textual search still wins for **literal prose** (comments, doc bodies, EXTERNAL_CAVEATS catalogues), **switch case literals** (`case 'x'`), **byte-anchored mass edits** (perl/python on file positions) and **exact occurrence counts** — the searcher resolves and de-duplicates, so it's the wrong ruler for "how many literal times". For the wired-in hot spots (verify an API exists before a wave, trace a type bug, walk declared caveats per cell), follow the entries in [`test/README.md` § "… find context fast (the searcher)"](test/README.md).

## Module / TypeScript conventions

- ESM-only (`"type": "module"`). **Relative imports must use the `.js` extension** even when pointing at a `.ts` file (`verbatimModuleSyntax` + `isolatedModules` are on). Type-only imports must use `import type`.
- Strictness is high: `strict`, `noUncheckedIndexedAccess`, `noUnusedLocals`, `noUnusedParameters`, `noImplicitReturns`, `noImplicitOverride`, `noPropertyAccessFromIndexSignature`, `noFallthroughCasesInSwitch`, `noUncheckedSideEffectImports`, `exactOptionalPropertyTypes`. Don't suppress these — fix the type.
- Target `es2023`, module `node20`, `rootDir: src`, `outDir: dist`. Indentation is 4 spaces (see [.editorconfig](.editorconfig)).
- With `exactOptionalPropertyTypes` on, `prop?: T` is not the same as `prop?: T | undefined`. Optional internal fields and `TsSqlErrorReason` union members spell out `| undefined` explicitly so callers can assign `undefined` to them. When you add a new optional field that may be assigned `undefined` (vs. just left absent), declare it as `T | undefined`.
- **Share, don't duplicate.** When a dialect override repeats a piece of the base, extract that piece into an overridable base method (precedent: `_buildInsertOnConflictUpdateSetColumns` in `AbstractSqlBuilder`, reused by the MySQL/MariaDB override); the extraction must not change any snapshot. Sibling methods share their core through a helper, not by building a string and delegating to each other (precedent: `__addOrderByClauseFromString`, shared by the `orderByFromString*` methods). A helper with a single caller stays inline.
- **Dialect emission fixes** use the capability hooks of the SqlBuilder (`_support…`, e.g. `_supportTableAliasWithAs`) and the context flags kept in `params` (`_set…(params, …)`, e.g. `_setResultingOperation`), not new special cases spread through the code.
- **Vocabulary:** say "data type", never "kind", for the type of a value. Align the text opportunistically when you touch it, never by mass replace: file names such as `with-values.kind-coverage.test.ts` stay, and "source kind" is plain English.

## When adding or changing public behavior

1. Implement in the relevant layer (`SqlBuilder` for dialect-specific SQL emission; `QueryBuilder` / `expressions` for the fluent API).
2. Document it in `docs/`, with its tests in `test/` (see "Writing and validating documentation" below).
3. The legacy [src/examples/](src/examples/) only gets minimal changes (see "Testing strategy"); new coverage, including driver-level execution, goes to `test/`.
4. Run the verifications before pushing. The minimum set:
    - `bun run validate` (src). For the **test** scope, use **`bun run validate:tests`** (the per-connector split) — see the memory box just below. CI gates the **src** scope via `build` / `validate` and the **test** scope via **`validate:tests`** (see [.github/workflows/ci.yml](.github/workflows/ci.yml)).
        - **Validating the whole test scope — `bun run validate:tests`.** It splits **one tsc program per connector** (`bash scripts/validate-tests.sh`): a single whole-matrix program over `test/tsconfig.json` + `src/` peaks past **17 GB** and OOMs 16 GB CI runners / most dev boxes, so it was removed. sqlite grew too large to split merely per-db, so every db is split the same way; configs are generated on the fly, no committed `tsconfig.<db>.json`. Peak = the single largest slice, not the sum (~8 GB; this is what CI gates; rationale in [scripts/validate-tests.sh](scripts/validate-tests.sh)). **It also takes coords** — the same vocabulary as the `tests` CLI (`<db>[/<version>[/<connector>[/<file>]]]`, glob + brace, quoted or not): `bun run validate:tests postgres/newest/pg` type-checks ONE cell in ~3 s against ~2 min for the full split. Because the matrix is symmetric a single type error appears in all 76 cells, so the way through a large type-surface change is one cell → the `types.negative` cells → one cell per database → the rest, not all at once. No coord = the full gate, unchanged.
        - **Inner edit-typecheck loop for tests — `bun run validate:tests:newest`.** A SINGLE tsc program ([`test/tsconfig.newest.json`](test/tsconfig.newest.json)) over every db's `newest` + `types.negative` cells (drops the older version tiers + `domain/`, mirroring `--run-versions newest`). It peaks ~14 GB — more than any slice of the full split — so on a 16 GB box run it alone; for a narrow change `validate:tests <coord>` is cheaper. A green newest run says nothing about the older tiers, so run the full `validate:tests` (pre-push / CI gate) before pushing. Both are runtime-agnostic (native `tsc` binary).
    - `bun run no-docker-examples` covers the legacy `src/examples/` suite without docker. CI runs it on Node 22/24/26 and Bun.
    - `bun run tests` runs the new `test/` matrix (mock-only). For the docker-backed real-DB pass add `--docker` (plus `npm run tests -- --run-connectors native` for Node's `node:sqlite`); for cross-cell WASM coverage add `--wasm`. For an inner iteration loop use `tests <coord>` or `tests --run-versions newest` — see "Test-loop discipline" above.
5. **Adding a public symbol or file**:
    - The public surface is **enumerated** in the `exports` map in [package.json](package.json) — wildcards are only used for the `__UNSUPPORTED__/*` escape hatch. A new file is *not* publicly importable until you add an explicit entry there.
    - If the new symbol is **cross-database**, also re-export it from [src/index.ts](src/index.ts) (the aggregated root entry consumers reach via `import 'ts-sql-query'`). Use `export type` / `export` correctly because of `verbatimModuleSyntax`.
    - **Database-specific** additions (per-connection, per-driver runner, error mapper) go only in the `exports` map by subpath, never in the barrel.
    - Documentation snippets should import cross-database symbols from the root entry with a trailing `// or 'ts-sql-query/<subpath>'` comment; database-specific symbols stay on their subpath.
    - Never widen the public surface by adding exports under `internal/`, `expressions/`, `queryBuilders/`, `sqlBuilders/`, `utils/` or `complexProjections/` — those remain reachable only via the `__UNSUPPORTED__/<original/path>` escape hatch.
6. **Writing changelog entries** in [docs/about/changelog/v2.md](docs/about/changelog/v2.md): write from the **library user's perspective**, not the contributor's. Describe what consumers will see — API additions, behavior changes, type-surface shifts, migration steps — and skip purely internal refactors that don't change the public surface. Internal-only work (compiler flag tightening, dependency updates, build-pipeline tweaks) goes under the **Internal changes** subsection and only when the user might still notice a side effect (e.g. a flag enabling stricter consumer typings). If a change doesn't affect anything a user imports, observes at runtime, or sees in their TS errors, don't add it to the changelog. A bug introduced and fixed within the same unpublished beta gets no entry: the reader of the release never saw it.

## Writing and validating documentation

The reader knows TypeScript and has used SQL, but doesn't have it fresh. A page must let them recall what each thing is, why it exists and when to choose it, and find everything the feature offers. [`docs/queries/compound-select.md`](docs/queries/compound-select.md) and [`docs/queries/select-page.md`](docs/queries/select-page.md) are the models.

**How a page reads:**
- It opens saying what the thing is and which questions it answers, in the reader's words, and what it can be confused with. Then what each option does, with one small worked example of data and result, when to choose each one and what it costs, what applies to what, and availability per database when it varies.
- Plain short sentences. Say what happens, not what the library "allows you to". No marketing, no filler, no internals, tests or `src/` paths in the prose of a user page. A warning box only for what can really surprise.
- **A query goes with its SQL and its parameters**, so the reader can turn to what they know. Only an example about an error that sends nothing goes without.
- A table when several things are compared on the same axes, and it must be complete. A page that names a word or option shows where it goes in the code.
- Sections in the order the reader needs: the everyday first, nothing that interrupts a topic or depends on something explained later. A title says what the section has; don't keep a bad one to protect an anchor. When a page moves, add it to `redirect_maps` in `mkdocs.yml`, which redirects files and not anchors.
- A typical way of doing something isn't the rule, and "on every database" needs all of them.

**Where things go:** `docs/queries` is what the query builder and the expressions do in the usual scenario: the `*IfValue` methods, the ignorable expressions and the order by, with sections that make the rest discoverable. `docs/dynamic` lets the reader discover every dynamic capability, with the complementary functions and types and the cases of dynamism, and it repeats what it needs to read coherently. Handling dynamic queries properly is a merit of this library: tell it with facts. Never describe the library by comparison with other libraries or drivers, on any page. Declarative queries come first: building conditions with `if`s is for the cases that need it.

**Scope of a page:** don't turn a page into an SQL course. A complex or advanced feature may deserve its own page; leave a short section with a link where a reader would look first. Don't remove a type or a list that a table replaces unless the table has everything they had.

**Tabs and code of the examples:**
- The per-database tabs are synced across the site: fixed labels in a fixed order, `=== "MariaDB"`, `=== "MySQL"`, `=== "Oracle"`, `===+ "PostgreSQL"` (the default), `=== "SQLite"`, `=== "SQL Server"`. Never combine two in one tab ("MySQL / MariaDB"). A `<name>` in a heading breaks its slug.
- Each `.join(x).on(...)`, `.innerJoin(...)` or `.leftJoin(...)` goes on its own line with its `.on`, never on the line of `selectFrom(...)`.
- The examples of the docs use the tables the doc-code templates declare (`tCustomer`, `tCompany`, … in `test/templates/doc-code/newest/documentation/<db>.ts`); the `docs.*` tests use the domain tables with the same shape, and the values of `test/db/<db>/domain/seed.sql`.

**Everything stated has a source.** Library behaviour: the code and a run. Engines and versions: [`test/ENGINE_SUPPORT.md`](test/ENGINE_SUPPORT.md), [`test/LIMITATIONS.md`](test/LIMITATIONS.md), the SQL builders, the markers of the matrix, or a real run. Without a source, don't state it. Inventory what the feature offers from the types before writing: what is offered and not explained is a gap. Check the signatures of `docs/api/*` against the types.

**A bug is not a warning.** When something surprises a reader, gives different results per database or contradicts its types, stop. Reproduce it on a real engine with a minimal case, compile it too, and bring what happens, the evidence, the severity and a recommendation. It may be a gap of the documentation and the intended behaviour, so don't change behaviour that a test fixes on purpose without asking.

**Before changing a snapshot, ask what that test proves.** A test that only compares SQL text doesn't prove the query does what its name says: make the failing test meaningful, with real rows, before fixing anything. Never make a function stop doing what its name promises, nor make a query worse, to satisfy a test or a rare case. Say where you'd touch before writing, and keep the change to what's needed.

**How deep to test what a page says.** Reviewing documentation has found more real bugs than most test rounds, because it asks what each thing promises. Keep that depth:
- **A claim isn't checked until it has run.** Each statement of behaviour gets a run: a worked table of results is produced by running it, not by reasoning, and a list of what a function accepts or rejects is tried value by value.
- **Compile it too.** Whether the types allow a case matters as much as what it does: write the probe, read the real error, and use `assertType<Exact<...>>` to pin the type. Add the rejected forms to the `types.negative` cells. A mock test proves the SQL text and nothing about the result.
- **Check rows, not only SQL.** For anything whose name promises a behaviour (`Insensitive`, `IfValue`, a page, a count), assert the rows on a real engine, with data that shows the difference: mixed case for `Insensitive`, a null in the list for `notIn`, a value with a wildcard for `contains`. Use a setting that really is what the test says it is: `collate "C"` proves nothing about insensitivity.
- **Probe every engine and version the claim covers.** A temporary test with raw SQL through `(ctx.conn as any).queryRunner` in `<db>/<version>/<connector>`, run with `--docker --docker-version closest`, answers what an engine really does; delete it afterwards and check `git status`. Compare at least the oldest and newest tier: PostgreSQL 17 and 18 differ in what `like` accepts, and MySQL 5.7 in what a parameter's collation does. PGlite and the sync cells have limits of their own.
- **Try the edges the reader will meet:** empty list, empty string, `null`, `undefined`, `0`, a value of another shape from JSON, text that looks like a number or a date, a one-letter name, a row without a match, a transaction refused before it begins, a wrapper around the runner, process time zone other than UTC set at launch (the suite pins UTC late, so it needs a spawned process).
- **Follow a surprise to its cause.** Before calling something a bug or a limit, find why: the history (`git log -S`, `git log -L`), who reads the method, what the driver does, what the engine's documentation says. A name or a test can be the wrong part; so can a remembered fact. Check it against the code and bring the evidence.
- **Read every failure.** An old tier failing is usually an engine limit: say which, with its marker and an entry in [`test/ENGINE_SUPPORT.md`](test/ENGINE_SUPPORT.md), and never mark before seeing the real error. A test that passes alone and failed in a whole run is flaky or environmental: rerun it alone, and say so. Discard any run that overlapped another heavy job.
- **A fix isn't done until the same run would have caught it:** the test fails before the fix and passes after, on the engine where it happened. After a change touching SQL text, check with a script that the snapshot diff has only the expected change, and don't accept a mass rebake unread.

**Validating a change of documentation**, one heavy job at a time:
1. Every new block of code has its test in `test/db/postgres/newest/pg/docs.<page>.test.ts`, with `// doc-start` and `// doc-end`, values of the real seed in `test/db/<db>/domain/seed.sql`, and snapshots left empty to be baked. The blocks of the docs are compiled and their SQL asserted by `bun run codegen:doc-code`, each block on its own against `test/templates/doc-code/newest/documentation/<db>.ts`: see [`test/DOC_CODE_EXTRACTOR.md`](test/DOC_CODE_EXTRACTOR.md). The generated cells are gitignored, so without regenerating them a stale file hides errors.
2. Propagate to the cells of each database, adapting what a dialect doesn't offer or marking it with `NOT-APPLICABLE` (not typed there) or `NOT-SUPPORTED` (an engine or version limit), with a new limit in [`test/ENGINE_SUPPORT.md`](test/ENGINE_SUPPORT.md). In `-sync` cells, `sync()` replaces `await`; a copied `await` passes silently there. A new test name goes in all cells, and `tests:audit` checks it. `tests:propagate`, `tests:mark` and `tests:sync-transform` do this mechanically (see their `--help`), and `docs:sql-tabs` writes the SQL tabs of a page's new blocks.
3. `bun run codegen:doc-code`, then `bun run validate:tests` (it stops at the first connector with errors, so repeat until it says all type-checked OK), `bun run tests`, `bun run tests:audit` and `bun run docs:check`. The audit tolerates `as any` and casts only in a test of exceptions through a helper with a `catch`, and treats `objectContaining` or `toContain` as weak matchers. `python3 scripts/llms.py --update-agents` updates the sizes in `docs/AGENTS.md`, and a new page must join an area of `scripts/llms.py`.
4. New tests on real engines, per version: `bun run tests '<db>/<version>/*/<file>.test.ts' --docker --docker-version closest`, one version at a time, and SQLite and PGlite with `--wasm`. Then `bun run tests:stop-containers`. Before publishing, the whole matrix on real engines too, with `npm run tests -- --run-connectors native` and `bun run no-docker-examples`. If the Docker disk fills up during a whole `--docker --wasm` run, run it per database, stopping the containers in between. A failure with `No space left on device` isn't a result.
5. Read the exit code of each step: `cmd | tail` hides it. Don't commit on a run you haven't read whole, and a script that commits on green must cover every step that ran.

**Reviewing docs with agents:** an agent reviewing a page touches only that page and its `test/db/postgres/newest/pg/docs.<page>.test.ts`. It runs no `tsc`, `validate*`, full matrix, audit, index, docker or examples. It may bake its own file, and run temporary copies on `postgres/newest/pglite` with `--wasm` or on `sqlite/newest/bun_sqlite`, which it deletes afterwards. It reports a suspected bug with a reproduction and writes nothing about it in the page. The coordinator propagates to the other cells; the reference cell of each database is `postgres/newest/pg`, `mysql/newest/mysql2`, `mariadb/newest/mariadb`, `sqlite/newest/bun_sqlite`, `sqlserver/newest/mssql` and `oracle/newest/oracledb`. MySQL and MariaDB use `onConflictDoUpdateSet`, not `onConflictOn`. A cell where every use of an import is commented out needs a `void` footer for it (see [`test/WRITING_TESTS.md` § Imports used only from commented-out blocks](test/WRITING_TESTS.md#imports-used-only-from-commented-out-blocks)).

**Reporting:** start with the result, say what was validated and how with real numbers and what wasn't, and separate what was confirmed from what was only read. Don't relay what an agent says as a fact: read it and check what matters. Say when pages were checked through agents' reports and not line by line. End with numbered decisions and a recommendation for each. Don't commit until asked, and keep bug fixes and docs in separate commits. A remark of the maintainer on a page applies to that page first, and then becomes a rule for the others.
