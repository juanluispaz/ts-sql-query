## Residual backlog — resolved (the audit's remit is the TYPED surface, not the emulated runtime)

The four residual items are **closed** — none is implemented. The decisive scoping principle: this audit
targets the **typed API surface** (type-branches a consumer observes), **not** runtime/emulated behaviour
(driver-layer result reduction, real-DB function execution, or per-version SQL *emission*). Three of the four
(R-P8b, R-W2, R-W3) are out of that remit. The fourth (R-P7) was investigated and confirmed to have **no
realization compatible with the suite's design principles** — so it stays closed too.

### ⛔ R-P7 · `sequence(...)` value-type keywords · **closed (degenerate — no principled realization)**
- **Gap:** **§ P** row **P7** — value-type keywords beyond `int` / `bigint` / `customInt` (`boolean` /
  `string` / `uuid` / `double` / `localDate*` / `enum` / `custom` / `customComparable` / `customUuid` /
  `customDouble` / `customLocal*`) have no dedicated assertion.
- **Why it cannot be done principled-ly** ([DESIGN.md § Principles](DESIGN.md#principles) #1 — every test runs
  through `ctx.conn`, asserts SQL + params + exact type + value, and **must potentially have passed through a
  real database**):
  - **Execution form** (declare the sequences as `DBConnection` members and test via the public API, like
    `sequence.next-current-value.test.ts`) — a sequence is an integer generator, so e.g. `nextValue()` over a
    `uuid` sequence is typed `string` while a real engine returns an **integer**. The mocked value is therefore
    a fiction **no real engine ever returns** → the test can never be real-validated → it is the
    "[mock-only is a smell](DESIGN.md#mock-only-smell)" anti-pattern. It also pollutes the realistic domain
    with nonsense sequences (`uuid_seq`, `string_seq`, …).
  - **Type-only form** (a never-constructed `class Probe extends DBConnection` reaching `protected sequence(...)`
    + index-type access) — emits no SQL, no params, no value and never touches `ctx.conn`, so it violates
    Principle #1 wholesale. (Attempted this session and **rejected/removed** for exactly that reason.)
  - The keyword → `*ValueSource` type mapping it would pin is, in any case, **already covered** by the
    `column()` / `const()` keyword fan-out (identical overload machinery).
- **Verdict:** degenerate. Stays closed, matching the original round-3 assessment.

### ⛔ R-P8b · `executeFunction` — the 12 NEW return-type keywords · **closed (out of typed-surface remit)**
- The **typed** aspect — return-type marshalling per keyword — is already exercised at the type level through
  the P2/P3 `fragmentWithType` / `aggregateFragmentWithType` keyword fan-out (`fragments.type-coverage.test.ts`).
  What remained was purely **runtime/emulated**: a user-defined DB FUNCTION per return type, ~12 types × 5
  engines ≈ **60 `CREATE FUNCTION` DDLs**, exercising the *driver* round-trip — not a typed-surface branch.
- Out of the typed-surface remit → **closed**. (If real-DB return-marshalling coverage is ever wanted as a
  separate effort, clone the existing `callEstimatedTotal` + `estimated_total` pattern per type; sqlserver
  names need the `dbo.` prefix; `sqlite` has no UDFs → NA.)

### ⛔ R-W2 · `MORE_THAN_ONE_ROW` / `ONLY_ONE_COLUMN_EXPECTED` · **closed (emulated runtime, not typed surface)**
- **Verified finding — the original "triggerable in mock mode" note was WRONG.** These reasons live **only**
  in `AbstractQueryRunner` (the base for real driver runners) and fire during *result reduction*.
  `MockQueryRunner` does **not** extend `AbstractQueryRunner` and returns the already-reduced value, so the
  guards never run: probing `ctx.mockNext([row,row]) → executeSelectOne()` yields **`INVALID_MOCKED_VALUE`**,
  and a 2-column `selectOneColumn` mock yields **`INVALID_VALUE_RECEIVED_FROM_DATABASE`** — never the two W2
  reasons. They are reachable **only** by a stub `AbstractQueryRunner` simulating a misbehaving driver, and
  `ONLY_ONE_COLUMN_EXPECTED` is a *defensive* guard unreachable via the public API on any well-behaved engine
  (`selectOneColumn` emits exactly one column).
- This is **emulated/runtime driver behaviour, not the typed surface** → out of remit → **closed**. (A stub
  runner could still lock the library↔driver contract if that coverage is ever wanted, but it is a
  `src/queryRunners/` unit test, not a type-branch.)

### ⛔ R-W3 · compatibility-version lower bands · **closed (no new cells; emitted SQL, not typed surface)**
- Decided: **no new `test/db/<db>/<version>/<connector>/` cells will be added.** Anything gated behind a
  `compatibilityVersion` band that no existing cell reaches is therefore out of test scope by construction.
  It is dialect-SQL **emission** coverage (emulated), not a typed-surface branch → out of remit → **closed**.

## O. ✅ Source bug — `MergeOptional` type ↔ runtime divergence (RESOLVED)

[src/expressions/values.ts:17-18](../src/expressions/values.ts#L17) (type) vs
[src/internal/ValueSourceImpl.ts:1972-1977](../src/internal/ValueSourceImpl.ts#L1972) (runtime) · **high
confidence — both lines verified verbatim**.

- The compile-time `MergeOptional` conditional maps `originallyRequired op requiredInOptionalObject` →
  **`originallyRequired`**. The live runtime `mergeOptional` (the one wired through `getOptionalType2/3` into
  every binary operator) yielded **`requiredInOptionalObject`** for the same input pair. So for an expression
  that combines a left-joined (`originallyRequired`) operand with an `asRequiredInOptionalObject()` operand,
  the **emitted result type and the runtime-produced projection shape diverged** (`flag: T` vs `flag?: T`) —
  and the two trip different keep-the-object rules at
  [AbstractQueryBuilder.ts:228-293](../src/queryBuilders/AbstractQueryBuilder.ts#L228) (`requiredInOptionalObject`
  → rule 1, drop unconditionally on null; `originallyRequired` → rule 2, drop only under an all-outer-join miss).
- The exported `__mergeOptional` ([values.ts:34](../src/expressions/values.ts#L34)) already matched the *type* but
  was only used by `FragmentQueryBuilder` — so the divergence was live for normal operators.
- **FIXED** in [ValueSourceImpl.ts:1973](../src/internal/ValueSourceImpl.ts#L1973): the runtime `mergeOptional`
  `originallyRequired` branch now reads `if (op2 === 'required' || op2 === 'requiredInOptionalObject')`, aligning
  it with both `__mergeOptional` and the `MergeOptional` type (the documented "select the less strict option"
  rule — `originallyRequired` is less strict than `requiredInOptionalObject`). Verified: `validate:tsgo` clean,
  full `bun run tests` 21273 pass / 0 fail, `no-docker-examples` ok — no existing snapshot regressed (the buggy
  pair simply had no prior coverage). Since the bug is fixed in `src/`, no `test/BUGS.md` entry is needed.
- **Follow-up (still open):** add the Q2 regression test — a projection combining a left-joined
  (`originallyRequired`) column and an `asRequiredInOptionalObject()` column through an operator, with `assertType`
  + SQL snapshot pinning the `?: T` (rule 2) shape — to lock the fix. No longer `// TODO[BUG]`-commented.
