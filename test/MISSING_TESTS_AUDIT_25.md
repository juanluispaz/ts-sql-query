### Found and fixed post-audit

- **CD-A4 (NEW — this round's A4 verdict was type-only; a runtime probe falsified it, then the fix landed).**
  The round marked the sole-optional-inner "misfire" **REFUTED** on the strength of a
  *compile-repro* (the inferred type was `wrapper: { inner?: … }` — `wrapper` **required**,
  rule-3). A **runtime probe** (the projector folding is library-side, identical mock/real)
  showed the type was **unsound for the collapse case**: when the sole inner object collapses
  (all leaves null / left-join miss) the projector **drops `wrapper` entirely** (default
  `asUndefined`) or sets it **`null`** (`projectingOptionalValuesAsNullable`), even though the
  type promised `wrapper` was always present — so `row.wrapper.inner`, type-safe per the
  required type, could throw / be `null` at runtime. **Reproduced** by a runtime probe and
  **docker-confirmed on all 5 real-server engines** (issue 3 all-null / project 4 no-issue
  reproduce the collapse identically) + native SQLite; **filed to `BUGS.md`**.
- **Fix — commit `143fe3b2`** (`src/complexProjections/projectionRules.ts`): `ContainsRequired` /
  `ContainsRequired2..5` were testing the rule-1/rule-2 discards and recursing on the **whole
  container** `TYPE` instead of the inner object `TYPE[K]`, and an optional inner contributed
  `false` (forcing the container required) instead of `never`. The fix recurses into
  `NonNullable<TYPE[K]>` and contributes `never`, so a container whose sole member is an
  optional inner object is now correctly **optional** (`wrapper?:` default) / **nullable**
  (`wrapper: … | null` under `projectingOptionalValuesAsNullable`) — matching the runtime.
- **Post-fix test sync** (same commit): the entry was removed from `BUGS.md` (empty again),
  the `docs/CHANGELOG.md` note added, and all **8** A4 tests/cell re-typed to the corrected
  shape with the `// TODO[BUG]` markers dropped — the 4 present-case tests renamed
  `…-object-makes-wrapper-optional-present-…` and the 4 collapse tests renamed
  `…-collapse-{drops,nulls}-wrapper-and-type-is-{optional,nullable}-…`. They now assert the
  corrected container type via `assertType` plus the collapsed runtime value
  (`{ iid }` / `{ iid, wrapper: null }`) and stand as permanent regression guards.

## CANDIDATE DEFECTS (verified emissions; maintainer adjudicates bug-vs-boundary)

### CD-1 — compound `orderBy(rawFragment)` is NOT no-table-restricted (STRONG; the round's headline) — FIXED in `726d9e77`

- **Where:** `src/expressions/select.ts:110` — `CompoundedOrderByExecutableSelectExpression.orderBy(column: IRawFragment<FROM[typeof source]>, …)`.
- **What:** on a compound (`union`/`intersect`/`except`/…), the value-source
  `orderBy` overload (`:109`) is **no-table-restricted**
  (`ValueSourceOf<NNoTableOrViewRequiredFrom<REQUIRED[source]>>`), but the
  **raw-fragment** overload (`:110`) is **FROM-scoped**
  (`IRawFragment<FROM[source]>`) — it accepts a raw fragment interpolating an
  **anchor-table** column.
- **Coordinator compile-repro:** `a.union(b).orderBy(conn.rawFragment\`${tProject.id} desc\`)` **compiles** (tProject is the compound's anchor; a fragment over the *union-branch* table `tIssue` is correctly rejected — `FROM[source]` = the anchor's source).
- **Coordinator runtime probe (mock):** it emits **unwrapped**
  `select name as label from project union select title as label from issue order by project.id desc`
  — a UNION whose ORDER BY references the base table `project`, which every engine
  rejects (a UNION's ORDER BY may only reference output columns/ordinals).
  Contrast the value-source overload, which both no-table-restricts **and** wraps
  (`select * from (…) order by …`).
- **Two readings:**
  - **Bug (leans this way — strong tells):** (1) this is the exact shape of a
    **confirmed+fixed** historical bug — "`orderBy(valueSource)` on a compound
    emits an un-wrapped `UNION … ORDER BY <expr>` that every engine rejects"
    (§9 ledger); the value-source arm was fixed, the **raw-fragment arm is the
    un-fixed sibling**. (2) The freshly-added **recursive** raw-fragment overload
    (`OrderByRecursiveAwareRawFragment`, `select.ts:566-568`) **IS**
    no-table-restricted **and negatively tested** (`types.negative/select.test.ts:67-68`),
    and its in-source rationale comment (`:551-559`) is literally *"just like a
    compound query's ORDER BY"* — i.e. the maintainer's own justification assumes
    the compound is already restricted, yet it is not. A no-table restriction
    would still allow the useful `rawFragment\`1\`` / `rawFragment\`label\`` cases
    (no table interpolation) and forbid only the invalid table-column
    interpolation, exactly mirroring the recursive twin.
  - **Escape-hatch (counter-reading):** `rawFragment` is raw SQL; the library may
    intend to leave scope-correctness to the user and only type the interpolated
    value-sources. Under [`LIMITATIONS.md`](./LIMITATIONS.md) "emit SQL the engine
    rejects" is not automatically a lib bug.
- **Resolution — FILED to `BUGS.md` post-audit.** The escape-hatch counter-reading
  collapsed against precedent: the recursive orderBy no-table fix (`df9d0838`)
  established as library policy that a compound/recursive ORDER BY **cannot** reference
  a specific table (its negative block literally says it "mirrors the restriction a
  compound query's ORDER BY carries"), so leaving the compound raw-fragment arm
  un-restricted is an inconsistency, not an intended escape hatch. Compile-verified
  both arms in all 6 dialects (`orderBy(tProject.id)` rejected; `orderBy(rawFragment\`${tProject.id}\`)`
  wrongly compiles). **Workaround shipped:** a compound-orderBy negative block in the 6
  `types.negative/select.test.ts` — the value-source arm locked with a live
  `@ts-expect-error`, the raw-fragment arm a currently-compiling call marked `// TODO[BUG]`.
  **Fix (fixing agent, `src/`):** narrow `:110` to
  `IRawFragment<NNoTableOrViewRequiredFrom<REQUIRED[source]>>` (matching the value-source
  sibling and the recursive twin) and activate the parked directive.

### CD-2 (recursive orderBy/limit/offset silently dropped by `forUseInQueryAs`) — FIXED in `726d9e77` (wrapping CTE)

- **Where:** `src/queryBuilders/SelectQueryBuilder.ts` — `orderBy`/`limit`/`offset`
  route to the outer `__recursiveSelect` via `__orderingAndPagingTarget()`
  (`:242-252`, `:362-383`); `forUseInQueryAs` discards `__recursiveSelect`
  (`:590`) and re-homes only the customization hooks.
- **Runtime probe (mock):**
  `recursiveUnion*(…).orderBy('id').limit(5).offset(1).forUseInQueryAs('tree')`
  emits `with recursive tree as (anchor union all recursive) select id from tree`
  — the **ordering and paging vanish entirely**.
- **The audit's "boundary" reading was REFUTED by a fuller probe.** The boundary
  argument rested on "the outer projection is replaced, so its clauses are dropped".
  But the plain-select and compound siblings under `forUseInQueryAs` do **not** drop
  them — they fold `order by`/`limit`/`offset` into the CTE body
  (`with x as (… order by … limit … offset …) select …`). Only the recursive path
  drops them, silently, and the dropped `limit`/`offset` changes which rows the CTE
  contains. So there **is** a render site; the recursive path just doesn't use it.
- **Conceptually valid SQL ⇒ missing feature (adjudication rule).** The intent is
  expressible as valid SQL and was **docker-verified on real PostgreSQL**:
  `with recursive tree_inner as (anchor union all recursive), tree as (select * from tree_inner order by id limit 5 offset 1) select … from tree`
  runs and returns rows. Since the concept is engine-valid, the library should render
  it — this was a **missing feature**, not a type-forbid bug.
- **Fixed in `726d9e77`**: `forUseInQueryAs` now renders the recursive result's
  ordering/paging on exactly this **wrapping CTE** (`… , tree as (select … from
  <recursive-member> order by … limit … offset …) select … from tree`) rather than
  dropping them; it does **not** naively fold into the recursive term. The test
  (`recursive-result-order-by-limit-offset-then-for-use-in-query-as`) is now a live
  regression guard asserting the rendered SQL + the correct paged value (issues 2, 3
  for `.limit(2).offset(1)`), docker-validated on the 5 real-server engines + native SQLite.

### CD-3 (recursive `beforeOrderByItems`/`afterOrderByItems` re-homed onto the CTE body) — FIXED in `726d9e77` (folded into CD-2)

- **Where:** `src/queryBuilders/SelectQueryBuilder.ts:580-585` (the `45c12968`
  allow-list) copies `beforeOrderByItems`/`afterOrderByItems` from the discarded
  outer `__recursiveSelect` customization onto the recursive CTE body. Two agents
  (F-RECENT, SEL-SEAM) converged on it; **src-verified** (the hooks are declared
  in `SelectCustomization` `select.ts:20-21` and copied at `:580-585`).
- **Runtime probe (mock) + docker:**
  `recursiveUnion*(…).customizeQuery({beforeOrderByItems, afterOrderByItems}).forUseInQueryAs('tree')`
  emits `with recursive tree as (anchor union all recursive **order by title asc, id asc**) select …`
  — the hooks render as an ORDER BY **inside the recursive CTE term**, which real
  PostgreSQL **rejects**: `ORDER BY in a recursive query is not implemented`.
- **The audit's "escape-hatch / not a bug" reading was REFUTED.** The hook content is
  **valid** (`title asc, id asc`); the invalidity is **structural** — `ORDER BY` is not
  allowed inside a recursive CTE term at all, so no user content could make it valid.
  This is the library placing valid content in an invalid **position**, not the user
  emitting bad raw SQL. Confirmed by the maintainer's own observation: recursive
  `orderBy` by column name renders validly on the **outer** select
  (`… select … from <cte> order by id`, docker-valid), so the library already has a
  valid ordering position — the hooks are simply routed to the wrong one. Per the
  "library-generates-conceptually-invalid-SQL ⇒ bug (it shouldn't emit it)" rule, it is
  a bug.
- **Same root and fix as CD-2** (folded into that entry), so **fixed in `726d9e77`** by
  the same wrapping-CTE render: `forUseInQueryAs` now renders the customize order-by hooks
  on `tree as (select … from <recursive-member> order by title asc, id asc)` instead of
  inside the recursive term. The test (`recursive-customize-order-by-hooks-then-for-use-in-query-as`),
  formerly block-commented because the SQL was engine-rejected, is now a live regression
  guard — docker-validated on the 5 real-server engines + native SQLite.
