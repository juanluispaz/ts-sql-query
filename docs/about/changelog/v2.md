# Change log of v2

To move an application from v1, see [Migrating from v1](migrating-from-v1.md). For the older versions, see the [change log of v1](v1.md).

## v2.0.0-beta.4

*Not released yet.*

**Groups of columns**:

The nested objects that a select and the `with` queries already accepted now work in the definition of a table, view or values, for reading and for writing.

**New features**:

- Oracle: `booleanStorage` on the connection says how the booleans are stored: `'number'` (the default, a `NUMBER(1)` with 1 / 0) or `'boolean'`, the `BOOLEAN` type of Oracle 23ai, written and sent natively (see [Oracle → How a boolean is stored](../../configuration/supported-databases/oracle.md#how-a-boolean-is-stored)). A `NUMBER(1)` column takes `new CustomBooleanTypeAdapter(1, 0)` with `'boolean'`.
- Oracle: `OracleDateAsTimestampTypeAdapter`, exported from `ts-sql-query/TypeAdapter`, declares a `localDateTime` or a `localTime` column stored in a `DATE`. The getters of the time (`getHours`, `getMinutes`, `getSeconds`, `getMilliseconds`, `getTime`), which Oracle rejects on a `DATE` (`ORA-30076`, `ORA-01821`), then work: they write the column as `cast(<column> as timestamp)`, and `getTime` counts the `DATE` itself; everywhere else the column is written as it is (see [Oracle → A date and time in a `DATE` column](../../configuration/supported-databases/oracle.md#a-date-and-time-in-a-date-column)).
- PostgreSQL: `useLikeInsteadOfIlike` on the connection writes the insensitive operations with a pattern with `like` instead of `ilike`, so a nondeterministic `insensitiveCollation` works in all of them from PostgreSQL 18. Without a collation they are written with `lower(x) like lower(y)` and still ignore case. By default they keep using `ilike` (see [the docs](../../configuration/collations.md)).
- SQLite: `sqliteRunsInApplicationTimeZone` on the connection says that SQLite runs in the zone of the application, so `getTime()` on a local text, the other getters of a time or a date time in the UTC and numeric formats, and `currentDate()` in those formats give what JavaScript gives for the same value. By default they work in UTC, as before (see [the docs](../../configuration/supported-databases/sqlite.md#the-date-functions-and-the-time-zone)).
- `transformProjection`, of a type adapter, of `DefaultTypeAdapter` and of the connection, writes the SQL of a value as it leaves the database, the pair of `transformValueFromDB`: the columns of the select that is executed, the columns of the `returning` of an insert, an update or a delete (on Oracle received as a text), the value of a function called with `executeFunction`, and each value inside the JSON of an aggregated array (`'aggregatedArrayValue'`: the SQL of a text, written as a JSON string) are written with the SQL it returns, and `transformValueFromDB` reads what arrives. The value keeps its SQL everywhere else: the where, the group by, the having, a subquery and a `with` use the value, an order by of the column orders by the value, and a compound select, or a distinct select ordered by the column, is written inside a select that converts its columns, so its rows are compared and ordered by the value; the distinct, the order by and the limit of a select used as an aggregated array also compare and order the value. `next.transformProjection` writes the conversion of the library, the text of a decimal on SQL Server. The type of where the value leaves, `ProjectionOutput`, is exported from `ts-sql-query/TypeAdapter` and the root `ts-sql-query` (see [the docs](../../configuration/column-types.md#the-sql-of-a-value-read-from-the-database)). A class of your own that implements `DefaultTypeAdapter` must implement `transformProjection` too.
- `ColumnGroupKeys`, `ExcludedColumns`, `WithoutExcludedPaths`, `ColumnsAtPaths` and `ShapeAtPaths` are also exported from the root `ts-sql-query`.
- A table, view or `Values` can group its columns in plain objects, like the two columns of a coordinate. Insert, update, on conflict, `Values.create`, insert from a select and the result of a select use the shape of the definition (see [the docs](../../configuration/mapping.md#grouping-columns)).
- The methods that receive column names (`ignoreIfSet`, `keepOnly`, `disallowIfSet`…) accept the path of a column in a group and the name of a group; a shape accepts paths and can have its own groups (see [the docs](../../queries/shapes.md#columns-in-a-group)).
- `dynamicPick` accepts `true` for a group of properties in its type, as `dynamicPickPaths` accepts its path.
- `asRequiredInOptionalObject()` on a column returns a column, so it can be used in the definition of a table, view or values. In a group, that column is required when the group is provided.
- `customBigint`: a column, constant, fragment, argument, function result or sequence with your own TypeScript type and the operations of a `bigint`, converted as a `bigint` (see [Column types](../../configuration/column-types.md)). Its filter in a dynamic condition is `CustomBigintFilter`. A `customInt` is converted as an `int`, and typed as `int4` on PostgreSQL: a value of your own type that needs 64 bits goes in a `customBigint`.
- `stringDecimal`: a column, constant, fragment, argument, function result or sequence of an exact decimal number whose value is a `string`, like `'12345678901234567890.1234567891'`, with no type name nor adapter: `this.column('amount', 'stringDecimal')`. It's sent, read, computed and compared as a `customDecimal` (below) on every database, and its type category is `'stringDecimal'`. It's compared only with another `stringDecimal` or a string, not with a `customDecimal`. Its filter in a dynamic condition is `StringDecimalFilter`. JavaScript has no decimal type yet ([TC39 proposal](https://github.com/tc39/proposal-decimal)); use `customDecimal` for a type of your own, like the one of a decimal library.
- `customDecimal`: a column, constant, fragment, argument, function result or sequence with your own TypeScript type for an exact decimal number, whose value is its text, like `'12345678901234567890.1234567891'` (see [Exact decimals](../../configuration/column-types.md#exact-decimals)). It's sent as text with a point as the decimal separator: as a `numeric` on PostgreSQL, and on MariaDB, MySQL and SQL Server as `cast(? as decimal(P, S))` with the digits of the value where it isn't assigned to a column, which the query runner writes, so a parameter you add to SQL you write gets it too. It's read with all its digits: as text from the driver, on Oracle fetched as text, and on SQL Server converted to text by the outermost query. A number the driver already turned into a JavaScript `number` is rejected with `PRECISION_LOST_RECEIVING_VALUE_FROM_DATABASE`, and a text that isn't a plain decimal with `INVALID_VALUE_RECEIVED_FROM_DATABASE`. `add`, `subtract`, `multiply`, `modulo`, `abs`, `sum` and the rounding functions return a `customDecimal`; `power`, the roots, the logarithms, the trigonometric functions and `average` return a `double`; there is no `divide`. A value wider than the decimals of the database is rejected with `INVALID_VALUE_TO_SEND_TO_DATABASE`: `decimal(65, 30)` on MariaDB and MySQL, `decimal(38)` on SQL Server, 38 significant digits on Oracle. SQLite has no exact decimal type: a `TEXT` column of a `STRICT` table keeps the text, and the new `decimalStrategy` of `SqliteConnection` says how the library computes and compares it, given in [the docs](../../configuration/supported-databases/sqlite.md#exact-decimals-the-decimal-strategies): `'decimal-extension and tsq-functions'` writes the functions of SQLite's decimal extension, plain SQL, and four functions of the library (`tsq_decimal_round`…) for what the extension lacks; `'decimal-functions'` writes them and functions of the library also for the order, the grouping, `min` and `max` (`tsq_decimal_key`…); `'text'` writes plain SQL and rejects the arithmetic with `UNSUPPORTED_QUERY`. Each has a canonical text variant (`' with canonical text'`, and `'canonical text'`), and the default is `'decimal-extension and tsq-functions with canonical text'`: the library writes and reads every value in its canonical text (`1.50` as `1.5`, so the scale isn't kept) and compares, groups and removes the duplicates by the text, which can use an index; the docs give the statement that turns the values a table has into it. `registerSqliteFunctions` registers the functions (see below). With `'decimal-functions'` a comparison and the order by use the key of the value, so an index on `tsq_decimal_key(column)` serves them. In every strategy an operation is exact or rejected before the query is sent, and the distinct aggregates count each number once (`1.5` and `1.50` are one); without the canonical text, a distinct select with a `customDecimal` column and a `group by` or an aggregate is rejected. Its filter in a dynamic condition is `CustomDecimalFilter`.
- `TypeCategory`, exported from `ts-sql-query` and `ts-sql-query/TypeAdapter`: the category of a type, the first argument of a column like `'customInt'`, or `''` when it isn't known.
- `getQueryParamType`, `getQueryParamTypeCategory` and `getQueryParamForceTypeCast`, in `ts-sql-query/queryRunners/QueryRunner`, give the name of the type, its category, and whether the database must receive the type of each parameter of a query; `setQueryParamType` keeps them in a query runner of your own (see [the docs](../../advanced/query-execution-metadata.md#get-the-type-of-each-parameter)).
- `MockQueryRunner` imitates a query runner of the library with the new `queryRunner` option, the name of its class (`'PostgresQueryRunner'`, `'BetterSqlite3QueryRunner'`, …): each parameter gets the placeholder, the cast and the value that query runner gives it, with the same code, so your function receives the SQL and the parameters the real query runner would send. `typesByName` passes the one of pg or Bun SQL (see [the docs](../../configuration/query-runners/general-purpose/MockQueryRunner.md#imitating-a-query-runner)).
- `isQueryParamValueForColumn`, in `ts-sql-query/queryRunners/QueryRunner`, says whether a parameter is the value given to a column of a table in an insert or in the set of an update, where the column gives it its type.
- `getQueryResultColumns` and `getQueryResultColumn`, in `ts-sql-query/queryRunners/QueryRunner`, give the columns of the result of a query: the name of each one in a row returned by the database, the property it fills, and the name and category of its type (see [the docs](../../advanced/query-execution-metadata.md#get-the-type-of-each-column-of-the-result)).
- SQLite: `registerSqliteFunctions(db)`, exported by the modules of `BetterSqlite3QueryRunner`, `BunSqliteQueryRunner`, `NodeSqliteQueryRunner` and `Sqlite3WasmOO1QueryRunner` (on sqlite-wasm `registerSqliteFunctions(db, sqlite3)`), registers on the database every SQL function the library may write, written in JavaScript without dependencies: the ones of the decimal strategies, `uuid`, `uuid_str` and `uuid_blob` of the uuid strategy `'uuid-extension'` (`uuid()` generates a version 7 UUID, whose values keep their order also within a millisecond: `Bun.randomUUIDv7()` on Bun, the library's generator elsewhere), and `ci_replace`. Every function but `uuid()` is deterministic, so it can be used in an index on an expression, and `decimal_sum` is also a window function. A decimal function or a `ci_replace` the database already has with the same name and number of arguments, like the ones of a loaded extension or one you registered, is left as it is; the uuid functions are always registered, replacing the version 4 `uuid()` some builds of SQLite ship (macOS's); `{ skip: [...] }` leaves out the ones you name, and keeps the database's. The uuid functions you registered yourself, as the docs showed before, keep working; the call makes them unnecessary (see [the docs](../../configuration/supported-databases/sqlite.md#registering-the-functions)). On node:sqlite it needs Node 22.16 or later.
- `getQueryConnectionConfiguration`, in `ts-sql-query/queryRunners/QueryRunner`, gives the connection that executes a query, to read its configuration: its `compatibilityVersion`, `uuidStrategy` and, on SQLite, how dates are stored and read. The values are the ones the connection has once built, including those a subclass sets in its fields (see [the docs](../../advanced/query-execution-metadata.md#get-the-configuration-of-the-connection)).
- `typesByName` in the options of the query runners of PostgreSQL, SQL Server and Oracle maps the name of a type to the type its parameters are sent with: the cast written by `pg`, `PgPoolQueryRunner` and Bun SQL (`'numeric'`), the oid sent by postgres.js and PGlite (`1700`, or on postgres.js a function giving the parameter), the type of `mssql` (`TYPES.NVarChar`, `TYPES.Decimal(18, 4)`), the `DbType` of `oracledb`. An exact decimal kept as text in a `customDouble` can now keep every digit on SQL Server too (see [Custom types](../../configuration/column-types.md#custom-types)). `PostgresQueryRunner`, `BunSqlPostgresQueryRunner`, the `mssql` query runners and the pool query runners of `oracledb` receive the options as a new optional second argument.
- `forceTypeCast(type, typeCategory, valueSentToDB, forceTypeCast, next)`, optional in a type adapter, and a protected method of the connection, decides whether the database must receive the type of a parameter where the library didn't ask for it. `ForceTypeCast` returns `true`, for a position the library doesn't detect, like a value inside a SQL fragment: `connection.const(10, 'int', new ForceTypeCast())` (see [the docs](../../configuration/supported-databases/postgresql.md#a-position-the-library-doesnt-detect)).
- `INVALID_VALUE_TO_SEND_TO_DATABASE` tells where the value is when it's in a `set` of an insert, an update or the update of a conflict, or in a row of `Values.create`: `tableName` has the table, or the name given to `Values.create`, `columnPath` has the property, with the name used in a shape, and `rowIndex` has the row when several are inserted, and always in a `Values`. Anywhere in the query, `paramIndex` has the position, from 0, the value would have in its parameters.

**Breaking changes**:

- A custom type (`customInt`, `customBigint`, `customDouble`, `customUuid`, `customLocalDate`, `customLocalTime`, `customLocalDateTime`, `enum`, `custom`, `customComparable`) needs its type name as the second generic argument: `this.column<RgbColor, 'RgbColor'>('ColumnName', 'custom', 'RgbColor')`. With only one generic argument, deprecated in v1, it doesn't compile; this applies to columns, constants, fragments, arguments, function results and sequences (see [Migrating from v1](migrating-from-v1.md#types-that-now-reject-what-compiled)).
- `transformValueFromDB`, `transformValueToDB` and `transformPlaceholder`, of a type adapter, of `DefaultTypeAdapter` and of the connection, receive the category of the type after its name: `transformValueToDB(value, type, typeCategory, next)`. An adapter or an override that calls `next` or `super` doesn't compile until it passes it on (see [Migrating from v1](migrating-from-v1.md#type-adapters-and-the-transforms-of-the-connection)).
- `transformPlaceholder` no longer receives `forceTypeCast`: `transformPlaceholder(placeholder, type, typeCategory, valueSentToDB, next)`. It receives the placeholder as the query runner wrote it, with the cast when there is one. To decide whether a parameter gets its type, implement `forceTypeCast`.
- `addParam` and `addOutParam` of the query runners receive the name of the type, its category and whether the database must receive the type of the parameter: `addParam(params, value, type, typeCategory, forceTypeCast)`, and return the placeholder as it is written in the SQL, with its cast when the query runner writes one. A query runner that forwards them, or code that calls them, must pass them. `setQueryParamType(params, index, type, typeCategory, forceTypeCast)` keeps them.
- SQLite: each strategy of dates and times as text now comes in two, by precision: `'localdate as text'` is now `'localdate seconds as text'` or `'localdate milliseconds as text'`, `'UTC as text using Z timezone'` is now `'UTC seconds as text using Z timezone'` or `'UTC milliseconds as text using Z timezone'`, and so on; the old names don't compile. A strategy writes all its values with the same width, and `currentTime()` and `currentTimestamp()` follow it. Before, the decimals were left out when the milliseconds were 0 and `currentTime()` and `currentTimestamp()` had none, so in the strategies with a `Z` a value without them sorted after one with them in the same second, and `lessThan`, `greaterThan` and `orderBy` gave the wrong answer. The default is now `'localdate milliseconds as text'`, which writes `.000` when the milliseconds are 0. The rows you already have may need [to be normalized](migrating-from-v1.md#sqlite-the-precision-of-the-dates-and-times-as-text) (see [the docs](../../configuration/supported-databases/sqlite.md#date-and-time-strategies)).
- `Sqlite3QueryRunner` and its subpath `ts-sql-query/queryRunners/Sqlite3QueryRunner` are removed: the `sqlite3` driver is deprecated by its maintainers. Use `BetterSqlite3QueryRunner` (`better-sqlite3`), `NodeSqliteQueryRunner` (`node:sqlite`), `BunSqliteQueryRunner` (`bun:sqlite`), `BunSqlSqliteQueryRunner` (Bun SQL) or `Sqlite3WasmOO1QueryRunner` (sqlite-wasm) (see [Query runners](../../configuration/query-runners/index.md#which-one-for-your-database)).
- The query runners reject, when they are created, a connection whose configuration would change the values the library receives, with `INVALID_CONFIGURATION` and the name of the setting: `pg` in the binary mode (`binary: true`, which reads a `numeric` wrong), a postgres.js `transform` of the results (`postgres.camel`, `column.from`, `value.from`, `row.from`) and its `infer: true` when the process doesn't run in UTC, a Bun SQL `transform` that renames the columns (`SQL.camel`, `column.from`), an `mssql` pool with `camelCaseColumns` or `columnNameReplacer`, with a `textsize` below the default of tedious (a longer text of a `max` type would be cut), or with `useUTC: false` when the process doesn't run in UTC, and `oracledb` without the environment variable `ORA_SDTZ` set to UTC when the process doesn't run in UTC. `MssqlPoolPromiseQueryRunner` rejects its first query instead. See the *Connection requirements* of each query runner, like [oracledb](../../configuration/query-runners/recommended/oracledb.md#connection-requirements).

**Behavior changes**:

- PostgreSQL: where PostgreSQL can't work out the type of a parameter, postgres.js and PGlite send the parameter with its type, and the SQL has no cast: `select $1 as result` instead of `select $1::int4 as result`. `pg`, `PgPoolQueryRunner` and Bun SQL write the cast as before.
- PostgreSQL: a `null` of a known type, like the value of `onlyWhenOrNull(false)`, is a parameter with its type instead of a literal: `$1::int4` with the parameter `null` on `pg`, `$1` with a `null` sent as an `int4` on postgres.js and PGlite, instead of `null::int4`.
- Oracle: a `null` parameter of a number, a date or a time is bound with its type, so the SQL no longer casts it: a row of `Values` is `values (:0, :1)` instead of `values (:0, cast(:1 as number))`, and the value of an optional column with a `CustomBooleanTypeAdapter` is `case :0 when 1 …` instead of `case cast(:0 as number) when 1 …`.
- postgres.js 4: the tests run with 4.1.0 (they ran with 3.4.9). `PostgresQueryRunner` accepts a connection reserved with `sql.reserve()` also in the types of postgres.js 4, where a reserved connection is no longer an `Sql`. The errors postgres.js 4 adds have their reason: `QUERY_TIMEOUT` is `SQL_TIMEOUT` with `timeoutType: 'statement'`, `QUEUE_TIMEOUT` is `SQL_TIMEOUT` with `timeoutType: 'connection'`, `TRANSACTION_ROLLED_BACK` is `TRANSACTION_ERROR` with `transactionErrorType: 'transaction rolled back'`, and the new authentication, TLS, batch and helper errors have theirs too; before, they were `UNKNOWN` ([docs](../../api/error-management/native-mappings/postgresql.md)).
- postgres.js: `connection.transaction(...)` whose statement failed, with the error caught, rejects with `TRANSACTION_ERROR` (`transactionErrorType: 'transaction rolled back'`) and the error of the statement as its cause, as with the other query runners. It rejected with the error of the statement.
- SQL Server with `mssql`: a parameter is bound by the category of its type, then by its name, and only a parameter without them (a query you wrote by hand) has its type inferred from the value. A `customInt` is bound as `int`, like an `int`; it was `bigint`, so a value of your own type that needs 64 bits goes in a `customBigint`.
- A `customInt`, `customDouble`, `customUuid`, `customLocalDate`, `customLocalTime` or `customLocalDateTime` is converted as the type of its category when its conversion isn't registered: before, its value was returned as the driver gave it, or as text from an array aggregate. On PostgreSQL, its parameter gets the type of its category where the library gives one: a `customDouble` is a `float8` also when its value is an integer, which was cast as `::int4`. See [Custom types](../../configuration/column-types.md#custom-types).
- `DynamicConditionForModel`: a branded `string` or `number`, like `string & { __brand: 'Semver' }`, has the operators of equality and comparison, with values of that type. Before it only had equality, as a union of literals.
- `in` and `notIn` with a subquery on an optional column return an optional boolean. Used as a value of a select, the property is now optional in the result type, and it's left out when the answer is null: before, the type said it was always there, and the query failed with `MANDATORY_VALUE_NOT_RECEIVED_FROM_DATABASE`, or on SQL Server and Oracle a null was returned as false.
- `PickValuesPathWitAllProperties` and `PickValuesPathWitAllPropertiesProjectedAsNullable` are now called `PickValuesPathWithAllProperties` and `PickValuesPathWithAllPropertiesProjectedAsNullable`; the old names are gone.
- The `extract*` functions, `ColumnKeys` and the other key types of `extras/types` now take the groups of columns into account: an object with columns inside another object used to be left out, and now it's kept with only its columns; the names of those columns are their paths (`'group.column'`).
- `SelectedRow` and the other selected types of a table only have its columns: an object in the class that is not a column used to appear in them.
- SQL Server, Oracle: `column.asRequiredInOptionalObject()` on a custom boolean column is written as any other selection of that column, so a null stays null, instead of being read as false.
- The `execute*` methods, `executeProcedure`, `executeFunction`, `transaction`, `beginTransaction`, `commit` and `rollback` report all their failures through the promise they return. Before, a query that couldn't be built (`MISSING_WHERE`, `DISALLOWED`, an invalid value to send…), a guard like `NOT_IN_TRANSACTION`, or a function given to `executeBeforeNextCommit` throwing in `commit` threw when the method was called, so a `.catch()` on the result didn't see them. A code using `await` inside `try` doesn't notice the change; a code ignoring the returned promise gets an unhandled rejection instead of an exception. The errors of the library raised while building the query now arrive as `TsSqlQueryExecutionError`, with the same `errorReason` and message, and the original `TsSqlProcessingError` in `cause`, so `instanceof TsSqlProcessingError` is no longer true for them. An error of your own code raised while building the query, like the one given to `allowWhen`, arrives as it is.
- `returningLastInsertedId()` after `onConflictDoUpdateSetIfValue`, `doUpdateSetIfValue`, `onConflictDoUpdateDynamicSet`, `doUpdateDynamicSet`, or after a method that can drop values from the update of the conflict (`ignoreIfSet`, `keepOnly`, `ignoreIfHasValue`, `ignoreIfHasNoValue`, `ignoreAnySetWithNoValue` and their `*When` forms), is typed `number | null`, and `returning(...)` and `returningOneColumn(...)` don't offer `executeInsertOne()`, as after `onConflictDoNothing`. When no column is left to update, the insert is sent as a do nothing, and a conflicting row now gives `null`; before, it was typed `number` and rejected with `MANDATORY_VALUE_NOT_RECEIVED_FROM_DATABASE` (see [the docs](../../queries/insert-on-conflict.md#when-nothing-is-left-to-update)).
- `executeFunction` reads its result as a column of a select is read, by the type you give: a `uuid` (or `customUuid`) result is converted from the form the database stores it in, as its parameters are sent in that form, with `bin_to_uuid` on MySQL with the `'binary'` strategy, `raw_to_uuid` on Oracle with the `'built-in'` and `'custom-functions'` strategies, and `uuid_str` on SQLite with the `'uuid-extension'` strategy. Before, the result came as the stored bytes and was rejected with `INVALID_VALUE_RECEIVED_FROM_DATABASE`. A function of yours that already returns the uuid as text must be declared with the result type `string` with those strategies.
- `commit()` rolls the transaction back when an `executeBeforeNextCommit` function fails, as `transaction(fn)` does. Before it left the transaction open, and a second `commit()` saved what that function had refused.

- The dates and times are in UTC, in any zone of the process: a `localDate` is read as a `Date` at 10:00 UTC of its day, a `localTime` as a `Date` on 1970-01-01 whose UTC getters are the stored time, and a `localDateTime` of a column without zone as a `Date` whose UTC getters are the stored digits; a `Date` is sent with its UTC getters. Read them with `getUTCHours()`, `getUTCDate()` and the other UTC getters. Before, with the process outside UTC, it depended on the driver: `pg`, PGlite, `mysql2`, `mariadb` and `oracledb` gave the digits of a `localDateTime` in its local getters, and postgres.js, Bun SQL and `mssql` in its UTC getters; a `localTime` was in its local getters except on SQL Server. A column with zone, like `timestamptz`, keeps its instant, as before. With the process in UTC nothing changes. SQLite keeps its strategies of dates. The [Time zones](../../configuration/time-zones.md) page is rewritten around this rule; see also [Migrating from v1](migrating-from-v1.md#dates-and-times-in-a-process-outside-utc).
- A `localTime` parameter is a `Date` on 1970-01-01 whose UTC getters are the time, on every database but SQLite, which keeps its strategies: the parameters your logs, `MockQueryRunner` and an `InterceptorQueryRunner` see, and what `next.transformValueToDB` gives a type adapter, are that `Date` instead of the text `'05:06:07'` on PostgreSQL, MySQL and MariaDB. Each query runner gives its driver the form it needs.
- SQLite: a `boolean` parameter is `true` or `false` in the parameters your logs, `MockQueryRunner` and an `InterceptorQueryRunner` see, instead of `1` or `0`; the query runners whose driver rejects a boolean give it as `1` or `0`.
- A `boolean` received as the text `true`, `false`, `t` or `f` is read in any case.
- A date or a time received as text whose digits are outside the calendar is rejected with `INVALID_VALUE_RECEIVED_FROM_DATABASE` instead of becoming another day: a day the month doesn't have, like `2024-02-30` (MySQL keeps it with `ALLOW_INVALID_DATES`), and the end of the day `24:00:00` (PostgreSQL's `time`, MySQL's and MariaDB's `TIME`).
- Oracle: a parameter of the `boolean` category of `executeProcedure` is bound as a PL/SQL `BOOLEAN`, so a procedure with a `BOOLEAN` parameter can be called. A procedure parameter of type `NUMBER` takes an `int` (see [Migrating from v1](migrating-from-v1.md)).
- The query runners no longer obey the settings of the driver that change a value in the queries of the library; they keep applying to your own queries through the driver: on `pg`, the parsers of `date` and `timestamp` (the others still apply); on PGlite, the parsers of `date`, `time` and `timestamp`; on `mysql2`, `dateStrings`, `supportBigNumbers`, `bigNumberStrings`, `decimalNumbers`, `rowsAsArray`, `typeCast` and `timezone`; on `mariadb`, `typeCast`, `rowsAsArray`, `metaAsArray`, `nestTables`, `decimalAsNumber`, `bigIntAsNumber`, `insertIdAsNumber` and `dateStrings`; on `mssql`, `arrayRowMode`; on `oracledb`, the global `fetchTypeHandler`, `fetchAsString`, `fetchAsBuffer` and `maxRows`. So a large integer is exact on `mysql2` and `oracledb` without configuring them.

**Documentation**:

- The change log is now split in [v2](v2.md) and [v1](v1.md), next to [Migrating from v1](migrating-from-v1.md), and the page of examples was removed.
- The files for AI agents are split further, so an agent reads less: `llms-queries-<database>.txt` has only what reads data, with common table expressions, compound and recursive selects in `llms-queries-advanced-<database>.txt` and the aggregates in `llms-aggregates-<database>.txt`, insert, update and delete in `llms-mutations-<database>.txt`, the transactions in `llms-transactions.txt`, and how to extend the library in `llms-extending-<database>.txt`. **Bug fixes**:

- `executeFunction` and `executeProcedure` write the name of the function or the procedure as it is given, also when it is a reserved word of the database: it was quoted, so a built-in function like `upper` failed on SQL Server (`[upper](@0)` is read as a function of the user without its schema). `escape` of the connection receives a third parameter, `allowReservedKeyword`, `true` for those names; an override of `escape` that quotes every identifier should keep them as they are.
- SQL Server and Oracle: the date functions of a `localDateTime` stored with an offset other than UTC (a SQL Server `datetimeoffset`, an Oracle `TIMESTAMP WITH TIME ZONE`) gave the parts of that offset instead of UTC: `getHours()` of `18:15 +09:00` was `18` on SQL Server, and `getDay()` gave the day of the offset on Oracle. They give the parts of its instant in UTC now, as the `getUTC…` methods of the `Date` read.
- Oracle: `getTime()` of a `TIMESTAMP WITH TIME ZONE` stored with an offset other than UTC counted the wall clock of that offset instead of its instant (`2024-01-14 19:30 +09:00` gave the milliseconds of 19:30 UTC). It gives the instant now, the same as the `getTime()` of the `Date` read, as in v1, and it also works on a `DATE`.
- Oracle: a `RETURNING` of a text over 200 bytes failed with NJS-016, after the row was written. The text is returned up to 32767 bytes, `returningMaxSize` in the configuration of the query runner changes it, and `typesByName` takes `{ type, maxSize }` for a type name; a value returned with the type `oracledb.DB_TYPE_CLOB` declared in `typesByName` is read as its text, of any length. Without it, a `CLOB` returned as text is limited to 4000 bytes by Oracle.
- `NodeSqliteQueryRunner`: a database opened with `returnArrays` gave each row as an array, and the library couldn't read it: the statements of the query runner give their rows as objects, and the database keeps the option for yours.
- Oracle: the `order by` of a compound query whose selects add columns with `customizeQuery({ beforeColumns })` named the column by its position, which the added columns move, so the rows came ordered by another column. It names the column now.
- SQLite with `Sqlite3WasmOO1QueryRunner`: a number without decimals beyond the range of a 64-bit integer, like `1e20` in a `double` column, was saved as a different number without an error (`1e20` as `7766279631452242000`, `1.5e300` as `0`). It's sent as a real, and the value saved is the one given.
- SQL Server before 2025: an array aggregate of a number of a wide `decimal` column, like a `customDouble` over a `decimal(38,10)`, failed with "Arithmetic overflow": the number was converted to an `nvarchar` of 30 characters, and it now has room for any `decimal(38)`.
- SQLite with the `Julian day as real number` format: `getHours()` of a time gave an hour 12 hours away, and a time or a date time read from the database could lose a millisecond (`.250` came back as `.249`).
- Oracle: a column whose name has one letter is no longer written between quotes, which made the database look for a lower-case column and reject the query.
- SQL Server with `mssql`: a `localDate` or `localTime` read by the library and sent back as a parameter of a query you wrote yourself was bound as `datetime2`: it's bound as `date` or `time`.
- `postgres` and Bun SQL: `LoggingQueryRunner` and `InterceptorQueryRunner` see the begin and the commit of `connection.transaction(...)`, which the driver runs by itself. A custom query runner implementing `QueryRunner` directly has the new method `executeInTransactionCallsBeginAndCommit()`, which says whether `transaction(fn)` goes through `executeBeginTransaction` and `executeCommit`; with `false`, the wrappers show those statements themselves.
- `connection.beginTransaction()` rejects with `LOW_LEVEL_TRANSACTION_NOT_SUPPORTED` when `lowLevelTransactionManagementSupported()` of the query runner is `false`.
- `MockQueryRunner`: a `null` in the rows your function returns is rejected with `INVALID_MOCKED_VALUE`.
- `NoopQueryRunner`: `executeSelectPage` returns an empty page, with `count` 0, instead of rejecting.
- SQL Server with `mssql`: a text of a `custom` or `customComparable` column is always sent as text. Before, the type of the parameter was guessed from how the text looks, so `version.equals('1.2')` was sent as a number, and the database raised an error converting the column.
- `dynamicConditionFor(fields, rules).withValues(filter)` accepts the rules in a filter written in place. Before, only a variable already typed with `DynamicCondition` compiled.
- A `Values` class with a nested object of columns compiled and failed on the database, and renamed the columns after the object.
- Compound selects compose as they are written: `a.union(b).intersect(c)` is `(a union b) intersect c` and `a.except(b.union(c))` is `a except (b union c)`, on every database. Before, the selects were written one after the other without grouping, so the database decided, and the rows could be different: PostgreSQL, MySQL, MariaDB and SQL Server did `intersect` first, and an operand that was itself a compound was read as part of the chain on every database.
- `executeSelectPage` counted the rows of the table when the select was an aggregate without `group by`, or an Oracle `connect by`: the total is now the rows of the select.
- A second `recursiveUnion*` on a recursive select compiled and failed on the database: it no longer compiles.
- The maximum of rows of `executeInsert`, `executeUpdate`, `executeDelete` and their `*Many` versions was ignored when there was no minimum.
- PostgreSQL: a property whose path was longer than 63 bytes lost its value without any error, or failed if it was required, because PostgreSQL truncates a long alias. A long alias is now written shortened, so the result is read correctly.
- An optional join used only in the `orderBy` was left out of the query, which the database rejected.
- `returningLastInsertedId` after an update of a conflict whose `where` isn't met returns `null`, as its type says, instead of throwing.
- MySQL: an insert from a select that reads the row to insert with `valuesForInsert()` in the update of the conflict compiled and failed on the database: it works from MySQL 8.0.19.
- A compound select with a constant in an object of left join columns could return the object without its required columns.
- `update` with only properties that aren't columns left in the values sent invalid SQL: it now sends nothing, as with no values at all.
- The `transactionSource` of an error leaving a transaction was the error itself, and the `stack` repeated it: it's now the place where the transaction was executed, once.
- `executeProcedure` and `executeFunction` didn't give the source of the execution to the query runner, so `getQueryExecutionStack` returned `undefined` for them.
- With a synchronous query runner, an error that made the transaction roll back was reported as its own `rollbackError`, even when the rollback worked.
- `SqlTransactionQueryRunner` and the other query runners that manage the transaction rejected `NOT_IN_TRANSACTION` with a native promise, which `sync()` refuses with `SYNCHRONOUS_PROMISE_EXPECTED`.
- `commit()` of a nested transaction, when an `executeAfterNextCommit` function failed, left the inner transaction as the current one: the metadata and the functions of the outer transaction were lost.
- A function of `executeAfterNextRollback` failing after an error of your own in the body of `transaction` gave a `TypeError`, and both errors were lost: it now rejects with the error of the function, with yours in `transactionError`.
- A rule of `dynamicConditionFor` returning a `dynamicBooleanExpressionUsing` with no conditions threw `DYNAMIC_CONDITION_INVALID_EXTENSION_RETURN_TYPE`: it now adds no condition.
- MariaDB: the rejection of a write in a `snapshot` transaction (`ER_CHECKREAD`, 1020) is `TRANSACTION_ERROR` with `serialization failure`, as on the other databases, instead of `SQL_INTERNAL_ERROR`.
- PostgreSQL: `equalsIfValue(null).and(true)` and similar conditions in a select, with a value left alone, failed reading the result, because the parameter came back as text.
- `dynamicPick` without a second argument, as when it comes from a request without that property, threw a `TypeError`: it now picks only the mandatory properties, as `dynamicPickPaths` does.
- `setIfSet` and `setIfHasValue` no longer count as giving a value to a required column of an insert: they only change what already has one, so `dynamicSet().setIfSet(...)` alone no longer compiles as executable.
- `DynamicPick`, `DynamicPickPaths` and the functions that use them stopped one level before what a select projects: the columns of an object at the fifth level couldn't be picked.
- In a fragment built with `buildFragmentWithArgsIfValue` or `buildAggregateFragmentWithArgsIfValue`, a `valueArg` of a custom type lost its type name, so it could be compared with a value of the same TypeScript type and another type name: it no longer compiles.
- `fromRef` compiled with a reference of another table or view, and gave it the columns of the table of its first argument: it no longer compiles.
- A function receiving a table, view or `Values` as `TableOrViewOf<typeof t>` or `TableOrViewLeftJoinOf<typeof t>`, without an alias, built with `fromRef` values that no query accepted: they had the source of any alias of the table instead of the one passed. They now have the source of the table or alias the function receives, so the function works in the query of the table and in the query of any alias of it. An aggregate of a column of that reference, like `connection.count(company.id)`, compiles there too; a nested aggregate is still rejected.
- An `or` with a subquery whose `where` has an `and`, like `exists(...).or(exists(...))`, wrote the subquery between extra parentheses: `(exists(select … where a and b)) or …`. They are gone; the query is the same.
- A select whose only column is an array aggregate, like `selectOneColumn(connection.aggregateAsArrayOfOneColumn(t.v))` or `selectOneColumn(connection.aggregateAsArray({ ... }))`, failed reading the result when executed with `executeSelectOne`, `executeSelectNoneOrOne` or `executeSelectMany`, with `INVALID_VALUE_RECEIVED_FROM_DATABASE`. It now returns the array, as when the aggregate is a property of an object.
- MySQL, MariaDB, Oracle: a `localDate` read and sent back didn't find its row, in any zone, with `mysql2`, `mariadb`, `oracledb` and Bun SQL: the date was sent with its time, and the database compared the `DATE` with a date and time. On Oracle, inserting it stored the time in the `DATE`. A `localDate` is now sent as the date alone.
- PGlite, postgres.js, Bun SQL and `mssql`: in a process west of UTC, a `localDate` was read as the day before, because these drivers give a date at midnight UTC and the library took its local day.
- PGlite: in a process outside UTC, a `localDateTime` read from a `timestamp` column and sent back moved by the offset of the process, so it didn't find its row and an update stored another value.
- Oracle: a `TIMESTAMP WITH TIME ZONE` column returned by `returning` came back shifted by its offset, also with the process in UTC.

## v2.0.0-beta.3

*Released on 5 Nov 2026.*

**Query runners, transactions and errors**:

Since the previous beta, the work moved from the SQL the library generates to what happens when it runs: the query runners, the transactions and the errors. Most of the changes below come from there.

- **Every query runner is now tested directly**, with hand-written SQL, against its real database.
- **The error mappings were checked against the real databases**, raising the errors on each engine, and corrected where they were wrong.
- **Transactions behave the same on every database**: the same isolation level names, a transaction the database rolled back no longer goes on as if it were open, and a query runner can share a transaction with another library or your own code.
- **Bun and the databases are up to date**: the Bun SQL query runners are no longer experimental, and the test suite runs against MariaDB 13.0 and MySQL 26.10, and against the older engine version each `compatibilityVersion` targets.
- **Aggregates and group by** were reviewed: new ways to group and filter by the columns of the select, and TypeScript now rejects what the databases reject.

**New features**:

- For AI agents: the package includes `AGENTS.md`, the documentation of its version in `docs/`, and in `llms/` one file per area and, for writing queries, per database; the website publishes the same from `llms.txt` ([docs](../ai-agents.md)).
- Export the filter types of dynamic conditions (`StringFilter`, `ComparableFilter`, `EqualableFilter`, …) from `ts-sql-query/dynamic/condition` and the root entry.
- Allow a query runner to run in a transaction managed by something else: new `forUseInTransaction` option in the query runners over a single connection; `PgLiteQueryRunner` and `MssqlPoolQueryRunner` also accept the transaction object of their driver ([docs](../../configuration/query-runners/combining-with-another-library.md#the-other-library-gives-its-connection)).
- Add `having(columns => …)` after the select, which receives the columns of the select, so a grouped expression with a parameter can be filtered (see [the docs](../../queries/aggregate-and-group-by.md#filtering-the-groups-by-the-columns-of-the-select)).
- Add `groupByNonAggregatedColumns()` to group by every column of the select that is not an aggregate, without listing them again (see [the docs](../../queries/aggregate-and-group-by.md#grouping-by-every-non-aggregated-column)).
- Add the `connection.anyValue(value)` aggregate function: any value of the group, for a column you don't want to group by (`projectName: connection.anyValue(tProject.name)`). Not available on MariaDB and SQL Server.
- Add `.concatIgnoringNull(...)` and `.concatIgnoringNullIfValue(...)`: a concatenation that reads `NULL` as an empty string, where `.concat(...)` gives `NULL`. The result is optional only when every operand is. Wrapping each operand in `.valueWhenNull('')` doesn't work on Oracle, where the empty string is `NULL`.
- The Bun SQL query runners are no longer experimental, except `BunSqlMySqlQueryRunner` against MariaDB, where a `Values` source can't be used ([docs](../../configuration/query-runners/recommended/bun_sql_mysql.md)).
- `SQL_RESOURCE_LIMIT_REACHED` now says which limit a statement too big went past, with the `resourceType` values `parameters`, `statement elements`, `statement length` and `statement complexity`, and the new `limit` field ([docs](../../api/error-management/error-types.md#a-statement-too-big-for-the-database)).
- Add the `SQL_USER_DEFINED_ERROR` error reason for the errors your own SQL code raises on purpose (`RAISE EXCEPTION`, `SIGNAL`, `RAISE_APPLICATION_ERROR`, `THROW`, ...). It carries the code, number and message you raised, in `databaseErrorCode`, `databaseErrorNumber` and `databaseErrorMessage`.
- Add the `MISSING_RECURSIVE_CONDITION` error reason: a recursive query whose linking condition ends up empty (every part an `*IfValue` without value) now fails with it. Depending on the database, it returned every row, never ended or failed at the recursion limit.
- PostgreSQL, SQLite: the `.where(...)` or `.dynamicWhere()` that follows `.doUpdateSet(...)` in an insert on conflict can use `valuesForInsert()`.

**Documentation changes**:

- New [Combining with another library](../../configuration/query-runners/combining-with-another-library.md) page, with [pg-boss](https://pgboss.io) and [Prisma](https://www.prisma.io) as examples.
- New [Aggregate functions, group by and having](../../queries/aggregate-and-group-by.md) page.
- New [Insert on conflict](../../queries/insert-on-conflict.md) page, with what wasn't documented.
- The [Transactions](../../queries/transaction.md) page now explains the isolation levels and what each database offers, the driver's connection, what happens when the database rolls back, and the deferred functions and metadata, with examples.
- The [mapping](../../configuration/mapping.md) page explains the kinds of columns of a table and what insert and update can do with each.
- Document what wasn't documented: inserting default values, constants, the neutral boolean, quoting identifiers, a select without a table, distinct correlated subqueries, dynamic `on` and `having`, `query()` and `params()`, and the `When` variants of insert and update.
- Each query runner page says which driver versions and runtimes it is tested on.

**Breaking changes**:

These are the changes to look at when coming from v1.

- Remove `PrismaQueryRunner`: Prisma 8 no longer offers the API it was built on. On PostgreSQL, Prisma 8 shares the pool and the transaction with the `pg` query runners ([docs](../../configuration/query-runners/combining-with-another-library.md#example-prisma)). To keep sharing a transaction with Prisma 7, stay on `v2.0.0-beta.2`.
- Rename `queryRunner.getCurrentNativeTransaction()` to `getCurrentNativeConnection()`, which now returns the connection of the transaction on every query runner, the pool ones included, and `undefined` outside a transaction.
- `queryRunner.execute(fn)` now calls `fn` with one argument, the connection to run statements on; with postgres.js, Bun SQL and mssql, `fn` received the pool or the client, and the transaction in a second argument ([docs](../../queries/transaction.md#using-the-drivers-connection-in-the-transaction)).
- A select with an aggregate and a non-aggregated column of a table no longer compiles without a group by; PostgreSQL, SQL Server, Oracle and MySQL reject it, and SQLite and MariaDB take an arbitrary row of the group. Use `groupByNonAggregatedColumns()` or `groupBy(...)`, or `anyValue(...)` for a column with the same value in the whole group.
- An aggregate function no longer compiles with an aggregate as its argument (`connection.max(connection.count(tIssue.id))`), except on Oracle. Aggregate over a subquery that aggregates.
- Oracle: `.orderingSiblingsOnly()` is no longer offered after the `.orderBy(...)` of a compound query, which Oracle rejects.
- Oracle: the parameters are now bound by name (`:0`, `:1`, ...). SQL given straight to the query runner must name its placeholders after the index of their value.
- SQLite: the queries now use numbered placeholders (`?1`, `?2`, ...), also with `MockQueryRunner` and `NoopQueryRunner`, so the generated SQL text changes: check your logs, test snapshots and interceptors that read it. SQL given straight to `BetterSqlite3QueryRunner` must use them too.
- Oracle: a statement executed outside a transaction is now committed, as on every other database; the pool query runners lost it and `OracleDBQueryRunner` left it pending. If you run a transaction of your own over that connection, use [`forUseInTransaction`](../../configuration/query-runners/recommended/oracledb.md#inside-a-transaction-something-else-manages).

**Breaking changes since v2.0.0-beta.2**:

These only affect what was new in v2: they are not breaking when coming from v1.

- The configuration of `PgLiteQueryRunner` is exported as `PgLiteQueryRunnerConfig`; it had the name of the one of `PgQueryRunner`, `PgQueryRunnerConfig`.
- Transaction isolation levels now use the SQL standard names plus `'snapshot'`, and each database offers only the levels it delivers; the others are a TypeScript error ([docs](../../queries/transaction.md#transaction-isolation)). The SQL sent to the database stays the same after renaming. To migrate:
    - PostgreSQL, MySQL, MariaDB: `'repeatable read'` is now `'snapshot'`.
    - Oracle: `'serializable'` is now `'snapshot'`.
    - No longer offered: `'read uncommitted'` on PostgreSQL (it runs as `read committed`) and Oracle, `'repeatable read'` on Oracle (Oracle refused both).
    - SQL Server: unchanged.
    - MySQL's `'snapshot'` doesn't prevent lost updates; MariaDB's does since 11.6.2 ([docs](../../queries/transaction.md#mysql-and-mariadb-snapshot-writes)).
- An isolation level is only accepted by the connection that built it with `connection.isolationLevel(...)`. A value typed with the bare `TransactionIsolationLevel` no longer compiles; type it as `ReturnType<typeof connection.isolationLevel>`.
- A statement with more parameters than allowed is now reported as `SQL_RESOURCE_LIMIT_REACHED` (`resourceType: 'parameters'`); it had a different reason on each driver, usually `SQL_INVALID_PARAMETER`. The maximum, which postgres.js and Bun SQL put in `expectedParameterCount`, is now in `limit`. Other errors of a statement too big keep their reason and gain a `resourceType`.
- The errors your SQL code raises on purpose are now reported as `SQL_USER_DEFINED_ERROR` instead of `SQL_ROUTINE_ERROR`, `SQL_UNKNOWN`, `SQL_CONSTRAINT_VIOLATED` or `SQL_INTERNAL_ERROR`, depending on the database. With `Sqlite3QueryRunner`, a trigger's `RAISE(...)` stays a constraint violation.
- The Bun SQL query runners now require Bun 1.4.4 or newer.
- `BunSqlMySqlQueryRunner` now requires a connection created with `foundRows: true` (or `?foundRows=true` in the URL), and throws `INVALID_CONFIGURATION` otherwise; without it, `executeUpdate()` only counted the rows whose values changed.

**Bug fixes**:

- The message of an error raised while reading a result repeated its reason (`NO_RESULT: NO_RESULT: …`).

Transactions:

- PostgreSQL: fix a transaction taken as committed when a statement failed and your code caught the error; the database had rolled it back and nothing was saved. Now the transaction fails with `TRANSACTION_ERROR` (`transactionErrorType: 'transaction rolled back'`), with the first error in its chain of `cause`, and `connection.transaction(...)` rejects and runs the after-rollback functions ([docs](../../configuration/supported-databases/postgresql.md#a-statement-that-fails-inside-a-transaction)).
- MariaDB, MySQL, SQL Server, SQLite: fix a transaction the database rolled back by itself going on as if it were open, with the following statements committed one by one; they are now rejected with the same `TRANSACTION_ERROR`. `Sqlite3QueryRunner`, `Sqlite3WasmOO1QueryRunner` and `BunSqlSqliteQueryRunner` can't detect it ([docs](../../queries/transaction.md#when-the-database-rolls-back-the-transaction)).
- SQL Server: fix the isolation level of a transaction staying on the pooled connection for later queries, which kept holding locks or refused reads.
- postgres.js, Bun SQL: fix a query runner created with `sql.reserve()` or with the transaction of `sql.begin(...)` failing when a transaction began. With a reserved connection the transactions run on it and you release it; inside a transaction of the driver, beginning another one rejects with `NESTED_TRANSACTION_NOT_SUPPORTED` ([docs](../../configuration/query-runners/recommended/postgres.md#using-a-connection-you-reserved)).
- `BunSqlMySqlQueryRunner`: fix `connection.transaction(fn, connection.isolationLevel(...))` failing with a syntax error.
- Pool query runners: an isolation level or access mode the database doesn't support is now refused by `beginTransaction`, and `executeConnectionConfiguration(...)` outside a transaction fails with `NOT_IN_TRANSACTION`.
- Allow a transaction begun from an `executeAfterNextCommit` or `executeAfterNextRollback` function to register its own end-of-transaction functions.
- Stop running the following `executeBeforeNextCommit` functions when one throws synchronously.

On MySQL and MariaDB, when the expression has parameters, it uses the position in the select list (`group by 2`), so don't add columns through `afterSelectKeyword` or `beforeColumns` in `customizeQuery` ([docs](../../queries/sql-fragments.md#customizing-a-select)).
- MySQL, MariaDB, SQLite: fix `orderBy('<column of the select>', mode)` ordering by a column of the table with the same name when the mode wraps the column in an expression, with no error. On MySQL, if that column has parameters, the query is wrapped in a subquery to order it.
- MySQL, MariaDB: a column of a table in a `having` is now written with the name of the table; these databases took it as the column of the select with the same name and filtered by that other value. If that column isn't in the group by, they now reject the query ([docs](../../queries/aggregate-and-group-by.md#a-column-that-isnt-in-the-group-by-in-the-having)).
- MySQL, MariaDB: the separator of `stringConcat` is now written as a literal, the only form these databases accept.
- PostgreSQL: fix `const(...)` and `optionalConst(...)` combined only with other parameters, which the database rejected or computed as text, giving wrong values (`const(7, 'int').lessThan(10)` was `false`).
- PostgreSQL: fix a fractional number as the operand of an `int` expression, and write the arguments of `executeFunction` and `executeProcedure` with their type.
- PostgreSQL: fix `.roundn(scale)` with a scale that is not an integer.
- Fix `.isNull()`, `.isNotNull()`, `.minValue(...)`, `.maxValue(...)` and, on Oracle, `.concat(...)` over a constant, which PostgreSQL rejected; they are now settled when the query is built, so the generated SQL is simpler and carries fewer parameters.
- Allow a fractional number where an `int` expression is compared or falls back (`.valueWhenNull(0.5)`, `.lessThan(2.5)`, `.in([0.5, 2])`, ...); it was refused when building the query. Writing a fractional value into an `int` column is still refused.
- SQL Server: allow composing `sequence(...).currentValue()` with other expressions.
- Oracle: fix `.concatIfValue(...)` without a value multiplying the size of the generated SQL.
- Fix a join whose condition ends up empty leaving out the `on`, which PostgreSQL, SQL Server and Oracle reject.
- Fix `update(...).from(...)` with `oldValues()` on PostgreSQL before 18 and SQLite, when a subquery reads a column of the `from` table.
- Fix an insert of several rows that sets a column with a sequence-generated primary key in only some rows.

Values and types:

- Fix the optionality of `.inN(...)` and `.notInN(...)` when an element can be `null`, which failed reading the row with `MANDATORY_VALUE_NOT_RECEIVED_FROM_DATABASE`, and allow elements of another table or with different optionality. A projected one changes its SQL on Oracle and SQL Server.

- These no longer compile, as the database rejects them or they always failed: `groupBy('name')` with an aggregate of the select, a second select with a column more in a compound query, and `insertInto(table).from(select)` with a column the table doesn't have.

## v2.0.0-beta.2

*Released on 27 Jul 2026.*

**Testing and quality**:

This beta's central focus was test coverage, and that work is what surfaced the long list of corrections below. The matrix-based test suite introduced in v2.0.0-alpha.4 had its major expansion here, and now covers close to every reachable line and branch of the library, exercised against real databases. What little remains uncovered is almost all extension points already wired for functionality not yet exposed, internal protections no public API can reach, or structural branches that don't apply to the case at hand.

- **Real, user-perspective tests — not unit tests of isolated functions.** Every test is a named scenario written the way you would write your own code: it touches only the public API and asserts four things together — the emitted SQL, the bound parameters, the exact TypeScript result type, and the returned value — through the same code path a real engine runs.
- **A mechanical quality gate over every test.** Building the suite meant building the tool that keeps it honest: a static quality gate — dozens of semantic checks run over the whole matrix on every push — that rejects any test which validates less than it should, no matter who wrote it. It flags an assertion that pins only a result's shape instead of its value, one that runs only against the mock and never a real engine, an un-baked snapshot, a silenced type checker, or a quietly disabled case, and it holds every cell in lockstep with the rest of the matrix. The whole suite passes it today with zero findings.
- **Validated against real databases, not only mocks.** Coverage was pursued against real databases for every supported engine, its compatibility versions and every driver, including running **older engine releases against their actual images** wherever the version can still be validated — a large effort, and the only way to catch version- and dialect-specific behavior a mock cannot.
- **A symmetric matrix, at real scale.** The suite is a matrix of cells — database × compatibility version × driver, 67 today — each running the same battery of tests (adapted where a dialect genuinely differs), so one behavior is checked across every engine, version and driver it applies to. The tests for a **single** cell already outweigh the core library code that connector runs by more than three to one; multiplied across the matrix, a full run is over a quarter of a million test executions (real-database and WASM passes included).
- **Three complementary audits pushed toward completeness.** Beyond line coverage (*what never ran?*), a type-driven audit asks *which capability the types advertise is never asserted?* and a semantic audit asks *where does the library promise one value and ask the engine for another, with nothing failing?* The latter two find defects a green suite hides — a declared `bigint` computed in floating point, a `getSeconds()` that can reach 60, a literal an engine reads as an exact type — and many of the fixes and obscure-behavior corrections below came from them, several long-standing.

**New features**:

- New [Collations & case sensitivity](../../configuration/collations.md) documentation page, and new tools to control collation and case sensitivity:
    - `.collate('<name>')` on a string value source forces a specific collation on a single value (case-sensitive/binary, case-insensitive, or language-specific), usable on either side of a comparison, on a projected/grouped/ordered column, or as a `replaceAll` argument.
    - `.replaceAllInsensitive(...)` / `.replaceAllInsensitiveIfValue(...)`: the case-insensitive twin of `replaceAll`.
    - `replaceCollation` (SQL Server, Oracle) names the collation forced on `replaceAll`'s match operands; `replaceInsensitiveCollation` (Oracle) names the case-insensitive collation used by `replaceAllInsensitive` when `insensitiveCollation` names none; `replaceAllInsensitiveFunction` (SQLite) names a user-registered function for `replaceAllInsensitive` (otherwise it falls back to a case-sensitive `replace`).
- Aggregate functions (`count`, `sum`, `average`, `min`, `max`, `stringConcat`, `aggregateAsArray`, their `Distinct` variants, and expressions built from them) are now rejected by TypeScript in `where`/`and`/`or`, `groupBy` and join `on` clauses, where SQL does not allow them; they remain allowed in `having`, `select` and `orderBy`. Compile-time only; the generated SQL is unchanged.
- Add support for marking a custom SQL fragment as an aggregate with `aggregateFragmentWithType` / `buildAggregateFragmentWithArgs` / `buildAggregateFragmentWithArgsIfValue` / `buildAggregateFragmentWithMaybeOptionalArgs`, so it gets the same clause checking. See [SQL fragments](../../queries/sql-fragments.md).
- Add support for `exactOptionalPropertyTypes`: an optional result property is now typed `k?: T` instead of `k?: T | undefined`, matching that ts-sql-query omits an absent optional property instead of setting it to `undefined`. With `exactOptionalPropertyTypes` disabled (the TypeScript default) both spellings are the same type.
- Allow `connection.transaction(...)` to receive a callback that returns a plain value instead of a promise, so a transaction can run fully synchronously under a synchronous query runner. See [Synchronous query runners](../../advanced/synchronous-query-runners.md).
- New `PRECISION_LOST_RECEIVING_VALUE_FROM_DATABASE` error reason for an integer value that cannot be represented in the requested type without losing precision, distinct from `INVALID_VALUE_RECEIVED_FROM_DATABASE`; it carries `value`, `typeName` and optional `rowIndex` / `columnPath`. See [Error management](../../api/error-management/library-raised-errors.md).
- New `usePlatformDependentRound` property on `MySqlConnection` / `MariaDBConnection`, with the same meaning it already has on `PostgreSqlConnection`.
- Unused `with` clauses (common table expressions the final query does not reference — for example one referenced only by an optional join that ends up pruned) are no longer included in the generated SQL.

**Documentation changes**:

- New [Collations & case sensitivity](../../configuration/collations.md) page: how collations work, each database's default, the language-dependent case-folding traps, which operations are affected, and every collation lever with a per-database reach table.

**Breaking changes**:

Each behavior change below keeps an opt-out that restores the previous behavior.

- PostgreSQL, SQL Server: `.minValue(...)` / `.maxValue(...)` now return `NULL` when an operand is `NULL` (matching the other databases and the declared optional type), instead of ignoring the `NULL` and returning the present value. Opt out with `ignoreNullInMinAndMaxValue = true`, or provide your own null-propagating function with `minValueFunction` / `maxValueFunction`. See [PostgreSQL](../../configuration/supported-databases/postgresql.md#minvalue-maxvalue-and-null) / [SQL Server](../../configuration/supported-databases/sqlserver.md#minvalue-maxvalue-and-null).
- Oracle: `.concat(...)` and the affix predicates (`startsWith` / `endsWith` / `contains` and their `Insensitive` variants) now return `NULL` when an operand is `NULL`, instead of reading the `NULL` as an empty string; previously an affix predicate built on a `NULL` search term matched every row instead of none. Opt out with `ignoreNullInConcat = true`, or provide a null-propagating package with `concatFunction`. If what you wanted was the ignore-`NULL` behavior of a *particular* concatenation rather than of the whole connection, use `.concatIgnoringNull(...)` (added in v2.0.0-beta.3) instead of the opt-out: it means the same thing on every database, and it does not change how the affix predicates treat a `NULL` search term. See [Oracle](../../configuration/supported-databases/oracle.md#concatenation-and-null).
- SQL Server, Oracle: `.replaceAll(...)` is now case-sensitive regardless of the database collation, so on a case-insensitive database it no longer replaces text of a different case. Opt out with `replaceCollation = ''`. See [Collations](../../configuration/collations.md#replacecollation-sql-server-and-oracle).
- SQL Server: `.length()` now counts trailing blanks (matching JavaScript's `String.length`), instead of using the native `LEN()` that excludes them. Opt out with `excludeTrailingBlanksInLength = true` (a genuine trade-off: the bare `len(x)` is lighter but under-reports by one for a value at its column's declared maximum length). See [SQL Server](../../configuration/supported-databases/sqlserver.md#length-and-trailing-blanks).

**Handling obscure database behaviors**:

These are not library bugs, but places where a database's — or its driver's — own surprising behavior produced a wrong or invalid result. ts-sql-query now smooths them over so the same code behaves consistently across every database, generally matching JavaScript. The new [Collations & case sensitivity](../../configuration/collations.md) and [Time zones](../../configuration/time-zones.md) pages give the deeper context.

- SQL Server: string operations on a `uuid` now work. A `uniqueidentifier` can't flow into a string operator, and a length-less `convert(nvarchar, …)` defaults to `nvarchar(30)` and overflows on a 36-character uuid, so `concat`, `.length()`, the `.asString()` a dynamic filter applies, and similar failed at runtime; uuids now convert to `nvarchar(36)` first. The same fix reaches an older-`compatibilityVersion` `aggregateAsArray`, which additionally truncated long strings (now `nvarchar(max)`) and lost `double` precision.
- MySQL, Oracle: a `customUuid` typed SQL fragment now reads the uuid back correctly. These engines store a uuid in binary, so the value needs the dialect's read conversion (`bin_to_uuid` / `raw_to_uuid`); the fragment now applies it, as a plain `customUuid` column already did.
- Filtering a `uuid` column with `notEqualsInsensitive` in a dynamic condition now works where a uuid isn't text. It applied `lower(...)` to the raw uuid (which PostgreSQL rejects) instead of its text form; it now casts to text first, and the rule — previously missing from the `customUuid` filter type — is accepted.
- `aggregateAsArray` / `aggregateAsArrayOfOneColumn` now return `bigint` values above 2^53 exactly. The aggregate comes back as JSON, and `JSON.parse` rounds a number beyond `Number.MAX_SAFE_INTEGER`; the library now parses it without rounding, so `bigint` / `int` / `double` / `customInt` / `customDouble` round-trip exactly.
- Reading an integer above `Number.MAX_SAFE_INTEGER` that a driver already rounded to a `number` now raises the clear `PRECISION_LOST_RECEIVING_VALUE_FROM_DATABASE` error, instead of returning the corrupted value (`int` / `stringInt`) or a misleading `INVALID_VALUE_RECEIVED_FROM_DATABASE` (`bigint`). To read such values exactly, enable your driver's big-integer mode or declare the column `bigint`.
- Oracle: `aggregateAsArray` / `aggregateAsArrayOfOneColumn` of a `localDate` or `localTime` column now works. Inside a JSON aggregate Oracle serialises a `DATE` with a midnight time and a time with a `1970-01-01` date prefix, which the `localDate` / `localTime` readers rejected; each now keeps only the relevant part.
- Oracle, SQL Server: a `localTime` value now binds correctly as a query parameter. Both drivers reject a bare `'HH:MI:SS'` string, so it is now bound as a date-anchored value, like `localDate` / `localDateTime`.
- Oracle: a `localDate` / `localTime` / `localDateTime` column read back through `RETURNING` now marshals correctly; the OUT bind now carries the column's type, so the driver returns a `Date` rather than an NLS-formatted string.
- Oracle: a `boolean` value the driver returns as a numeric string (`'1'` / `'0'`) now reads correctly, coerced the way the `int` / `bigint` read path already did.
- Oracle: a multi-row `INSERT` now reports the number of inserted rows. Oracle emits it as a PL/SQL block, for which drivers report no row count, so it previously returned `0`; the count is now supplied, and the `min` / `max` bounds of `executeInsert(min, max)` enforce correctly.
- Oracle: an `ORDER BY` in a subquery is now honoured. Oracle needs a row-limiting clause for it to take effect, so it was rejected in an inline one-column select and silently ignored in a `WITH` body or derived table; a no-op `offset 0 rows` is now emitted, as SQL Server already did.
- `divide(...)` now always divides in floating point, matching JavaScript's `/`. It left the choice to the engine when both operands were exact, so MySQL / MariaDB truncated `1 / 3` to 4 decimals; the dividend is now cast to floating point when neither operand already is (and the cast is dropped when unnecessary). Only the result changes, on MySQL / MariaDB.
- MySQL, MariaDB: `asDouble()` now really produces a double. `<value> * 1.0` is an exact (DECIMAL) literal here, so it was a no-op and later fractional operations truncated; it now emits a real cast to double.
- `asInt()` / `asBigint()` on a double now compute in integer arithmetic. Both declared an integer to TypeScript but left the SQL floating point, so downstream integer math ran in floating point (and `.modulo(...)` was rejected on SQL Server); the value is now cast to a 64-bit integer type.
- MySQL, SQL Server: `cbrt()` no longer loses significant digits — its `1.0 / 3.0` exponent was an exact literal division these engines truncate; it now uses a floating-point exponent.
- MySQL, MariaDB: `average()` no longer truncates an exact column (`avg(<int>)` answered in an exact type cut at 4 decimals); the operand is now cast to floating point first, as SQL Server already did.
- MySQL, MariaDB: `.round()` keeps breaking ties away from zero regardless of what came before it in the chain (these engines defer an approximate operand to the platform's round-half-to-even); opt into the platform-dependent behavior with the new `usePlatformDependentRound`.
- SQL Server: `.power(...)` on an integer receiver no longer truncates the fractional result to `int` (T-SQL's `POWER` takes its first argument's type), so `intColumn.power(0.5)` no longer returns `1`.
- PostgreSQL, SQL Server: `.modulo(...)` with a `double` / `customDouble` operand now emits valid SQL; neither engine accepts `%` on a floating-point operand, so it now uses `mod` / a `numeric` cast.
- `.valueWhenNull(...)` no longer mistypes its fallback: on SQL Server it narrowed a wider or longer fallback to the receiver's type (`isnull` coerces to its first argument, so `.valueWhenNull('abcdef')` on a `varchar(3)` returned `'abc'`), now `coalesce`; and on any database a `double` fallback on an `int` receiver rejected a fractional value, now the declared type is promoted to `double`.
- MySQL, MariaDB, Oracle: `getTime()` is now correct outside the 1970–2038 window (MySQL / MariaDB's `UNIX_TIMESTAMP()` returns `0` / `NULL` there, and Oracle's formula was a day off); all three now agree with JavaScript across the full `Date` range. This is a date-range fix, not a time-zone fix — see the new [Time zones](../../configuration/time-zones.md) page.
- PostgreSQL: `getSeconds()` no longer reports a 60th second and `getMilliseconds()` no longer wraps to 0 — the `::integer` cast rounded the sub-second fraction, which is now truncated first.
- MySQL, MariaDB: `getMilliseconds()` no longer returns 1000 (a rounding tie broke upward); the sub-millisecond part is now truncated. Only reachable on a `DATETIME(6)` column.
- SQL Server: `getDay()` no longer depends on the session's `SET DATEFIRST` (which shifts the weekday under most European languages); it is now rebased so 0 is always Sunday, like JavaScript's `Date.getDay()`.
- SQLite: several date accessors reading a Unix-time-milliseconds value are now exact — a lost millisecond below 3.42, an off-by-one on pre-1970 instants (SQLite's integer division truncates toward zero), and an off-by-one in `getMilliseconds()` are all corrected.
- MySQL, MariaDB: `.length()` now counts characters, not bytes, matching JavaScript's `String.length` — so `'café'.length()` answers `4`, not `5`. `LENGTH()` counts bytes on these engines; it now emits `char_length()`.
- `substr` / `substring` now follow the JavaScript definition for negative and out-of-range indexes, and `substrToEnd` / `substringToEnd` are no longer identical: a negative index counts from the end for `substr` and clamps to 0 for `substring`, and `substring(start, end)` swaps its arguments when `start > end` instead of emitting a negative length (rejected by PostgreSQL). Requires the index sign known at build time; a value-source index is unchanged.
- SQL Server: `substrToEnd` / `substringToEnd` now return the same value on every `compatibilityVersion` and no longer fail when the start index runs past the end (the older emulation cut trailing spaces and could compute a negative length); they now return `''` for an out-of-range start.

- MariaDB, MySQL: `.or(...)` on a multi-table `DELETE` / `UPDATE` join `on` clause emitted `AND` instead of `OR`, matching the wrong rows.
- SQL Server, Oracle: a non-column boolean value used as a condition (a `const(..., 'boolean')`, a boolean inline subquery, an already-boolean `valueWhenNoValue(...)` fallback) emitted `((@0 = 1) = 1)`, which SQL Server rejected; now emits `(@0 = 1)`.
- A `CustomBooleanTypeAdapter` subclass's `transformPlaceholder` was dropped when the column was re-projected through a `with` view or inline subquery; it is now preserved.
- SQL Server, Oracle: `.isNull()` / `.isNotNull()` on a column with a `CustomBooleanTypeAdapter` tested the adapter's remapped `0` / `1` expression instead of the stored column, so it answered the wrong question — on Oracle `isNull()` never matched any row and `isNotNull()` matched every one; on SQL Server `isNotNull()` also matched rows storing `NULL`. Both now test the column itself.
- Shaped INSERT / UPDATE (`shapedAs({ ... })`): several parts of the surface were typed against the real column names instead of the renamed shape keys — the conditional `*When` set / `ignoreIf*When` / `keepOnlyWhen` methods, the `disallow*` guards, the `onConflictDoUpdateSet({ ... })` one-shot, `setIfValue` for a defaulted non-nullable column, and `extendShape(...)` on the where-required path — so they rejected the key they actually map or silently dropped it. All now accept the renamed shape keys.
- `extendShape({ ... })` mishandled a shape value written as a column object instead of a column name (an `UpdateShape` value may be either): adding a **new** key that way always threw `INVALID_SHAPE_OVERRIDE`, while **re-declaring** an existing column-valued key with a column name was silently accepted — exactly the collision the error exists to report. Both now test the key already in the shape.
- MariaDB, MySQL: a shaped `INSERT … ON DUPLICATE KEY UPDATE` reusing a renamed shape key dropped the whole update clause, silently becoming a plain `INSERT` that then raised a duplicate-key error.
- A single-row INSERT's `keepOnlyWhen(true, …)` on a `dynamicSet()` insert wrongly let `executeInsert()` compile while a required column was still unset; its result type now matches `keepOnly`.
- MySQL: an `INSERT … SELECT … ON DUPLICATE KEY UPDATE` (8.0.19+) appended an invalid `AS _new_` row alias after the `SELECT`, rejected at parse time; the from-select form now omits it.
- A table/view customization (`createTableOrViewCustomization`, e.g. a `withSqlHint(t)` wrapper) was dropped when the wrapper was re-aliased with `.as(...)` or made left-joinable; it now follows the clone.
- `projectingOptionalValuesAsNullable()` dropped its optional-null leaves, or failed to type-check, in several compositions — a compound query (`UNION` / …, where the method was also missing from the type), the elements of an inline aggregated array or an inlined one-column aggregate, and after a chained array-shape modifier or `allowWhen` / `disallowWhen` gate; all now keep the optional leaves present as `null`.
- Optional nested objects in a projection were mistyped after the v2 rework: an optional nested object was typed `{ … } | null` (it is omitted at runtime, never `null`), its non-required properties were typed as present keys carrying `| undefined` instead of optional keys, and a container whose sole member is an optional inner object was typed required. All now match the runtime.
- A projected optional object drawing its table leaves from one left join plus an always-present `const` leaf was mishandled on a join miss — dropped when the `const` should keep it, or kept when the type says drop it; both cases now match their declared type.
- Ordering a compound query (`UNION` / `INTERSECT` / `EXCEPT`) by an expression — a value source, a value source inside a raw fragment, or `nulls last` / `nulls first` — emitted a bare term the strict engines reject; PostgreSQL, SQLite and Oracle now wrap the compound, while MySQL / MariaDB keep it inline. (SQL Server cannot order a compound by a bare bind parameter.)
- Ordering a compound or recursive `SELECT` result by a table-bound expression is now a compile-time error instead of invalid SQL, since the base tables are out of scope there; order by the projected column name or `orderByFromString` instead.
- `orderBy` / `limit` / `offset` and the `customizeQuery(...)` hooks of a recursive `SELECT` landed on the CTE anchor member instead of the whole recursive query (so ordering paged the recursion seed, and hooks were mislanded or dropped); they now apply to the final result and survive being consumed as a CTE via `forUseInQueryAs(...)`, and `executeSelectPage()` on a recursive result now returns the true total.
- A one-column recursive `SELECT` used as an inline value (`forUseAsInlineQueryValue()`) threw `INTERNAL`; it now emits a valid scalar subquery, and its aggregated-array form produces a scalar array.
- PostgreSQL (below 18): an `UPDATE … FROM` reading pre-update values via `oldValues()` and projecting a joined-in column through a nested `RETURNING` object emitted invalid SQL; the nested column is now handled like a top-level one.
- `executeSelectPage()`'s count query no longer carries the page's `ORDER BY` (pure cost, since it can't change the count), and now keeps the `customizeQuery(...)` hooks on a plain `SELECT`'s count.
- `subSelectUsing(...)` / `subSelectDistinctUsing(...)` mistyped the fifth correlated table, so five distinct outer tables failed to compile; the positions are now inferred independently.
- `buildFragmentWithMaybeOptionalArgs` dropped an optional value-source argument's optionality when it followed a plain-value argument, typing a possibly-`null` column as required; the result is now optional whenever any argument is.
- `between` / `notBetween` and the `substr` / `substring` / `replaceAll` operations built from two value sources computed the result's optionality from only one operand while the type merged both; the runtime now merges both.
- `extractProvidedIdColumnNamesFrom` (`ts-sql-query/extras/utils`) declared the wrong return type (naming the autogenerated keys, a copy/paste slip); it now returns the provided primary-key column names.
- `UpdatableOnInsertConflictRowShapedAs` (`ts-sql-query/extras/types`) rejected value sources because it was defined as the literal-only *Values* form; it now accepts them, like the non-shaped `UpdatableOnInsertConflictRow`.
- A multi-row `INSERT` with a bare `onConflictDoNothing()` still exposed `executeInsertOne()` on its `RETURNING` path even though the conflict can suppress every row; it now matches the other insert forms.
- `Values.create(...)` stopped type-checking its rows during the v2 cycle (accepting a missing required column, a wrong-typed value, or an undeclared key); rows are validated again, and the `extras/utils` writable-column extractors return a `Values` view's real columns.
- Empty operations no longer misbehave: an empty-batch `INSERT` (`values([])`) with a `RETURNING` clause sent an empty query to the driver (the `RETURNING` shapes now short-circuit like the plain `executeInsert()`), and the `min` / `max` bounds of `executeInsert` / `executeUpdate` / `executeUpdateMany` were skipped on an empty operation (now enforced, so `min > 0` rejects with `MINIMUM_ROWS_NOT_REACHED`).
- A mutation with an empty `returning({})` projection emits no `returning` clause, but its result was still read back through the driver's data-returning path: `deleteFrom(...).returning({}).executeDeleteMany()` threw on better-sqlite3 (`This statement does not return data`) and resolved a driver result object instead of an empty array on MariaDB. It now runs as a plain mutation and resolves `[]`.- A single-row `returningLastInsertedId().executeInsert()` resolved `null` when the database returned no id, though its type promises the id; it now rejects with `MANDATORY_VALUE_NOT_RECEIVED_FROM_DATABASE`. (The `onConflictDoNothing()` form, typed `number | null`, is unchanged.)
- An `INSERT … ON CONFLICT DO UPDATE` whose update set resolved to no columns dropped the whole conflict clause, silently becoming a plain `INSERT` that raised a unique violation; it now degrades to a conflict-ignoring no-op.
- SQLite: `returningLastInsertedId()` after `onConflictDoNothing()` returned a stale id when the row was suppressed, on `compatibilityVersion` below 3.35; it now resolves `null`.
- A dynamic condition error's `errorReason` reported a wrong `path` and value (nested keys ran together, and a non-object filter value pointed at the enclosing scope); both now report the full dotted path and the offending value.
- SQL Server, Oracle, MySQL, MariaDB: `startsWith` / `endsWith` / `contains` (and their `not` / `Insensitive` / `IfValue` variants) mis-escaped a literal wildcard (`_`, `%` or `\`) in the search text, matching the wrong rows; each is now escaped correctly. Only affected real databases.
- MySQL, MariaDB: `orderBy` dropped the case-insensitivity of the `asc nulls last insensitive` and `desc nulls first insensitive` modes; now applied. Only visible on a case-sensitive collation.- Continuing to build a dynamic query after it was already rendered — calling `query()` / `params()` or executing it, then adding another `set` / condition / clause — reused the previous rendering's parameter list, so the new statement's placeholders were misaligned and any `with` clause the addition introduced was left undeclared (rejected by the engine). The cached rendering and its parameters are now discarded whenever the query changes.
- Stacking two query-runner wrappers (for example a `ConsoleLogQueryRunner` around an `InterceptorQueryRunner`) logged a duplicate set of synthetic `beginTransaction` / `commit` / `rollback` events per transaction: a wrapper judged its transaction-management capability by asking whether the runner it wraps is a **mock**, instead of reading the wrapped runner's real capability. The events are now reported once. Only affected chains of two or more wrappers.
- A deferred transaction hook (`executeBeforeNextCommit` / `executeAfterNextCommit` / `executeAfterNextRollback`) that returned a **rejecting** promise leaked an unhandled rejection, and a second failing async hook had its rejection dropped so the transaction resolved as if it had succeeded. The transaction now rejects with `ERROR_EXECUTING_DEFERRED_IN_TRANSACTION` (extra failures attached via `additionalErrors`), and no rejection escapes unhandled.
